## Purpose

This document defines the functional and non-functional requirements of the AIDLC Starter Kit v2.0.0, the AI-Assisted Development Lifecycle toolkit for Texas.gov Digital Government Services (TDGS). It describes **what** the kit provides — its capabilities, user interactions, and quality attributes — without prescribing implementation details.

Requirements are organized by capability area and numbered sequentially (FR-1 through FR-N). Non-functional requirements are included selectively, covering only the quality categories that apply.

## Scope

The AIDLC Starter Kit is a collection of 33 Copilot prompt files, 11 custom skills, user guides, test suites, and CI/CD automation that enables AI-assisted software delivery within a multi-repository VS Code workspace. It depends on BMAD v6.3.0 for planning and implementation skills, and targets GitHub Copilot agent mode as its execution environment.

### In Scope

- Copilot prompt commands for all phases of the delivery lifecycle
- Custom skills extending the BMAD skill set
- Workspace configuration and setup automation
- Three-layer testing infrastructure (unit, API, functional)
- Sprint tracking, dashboarding, and metrics
- Knowledge base generation and synchronization
- CI/CD integration via GitHub Actions
- User documentation for all roles

### Out of Scope

- BMAD framework internals (covered by the BMAD specification)
- Application code generated by prompts (project-specific)
- GitHub platform administration (org settings, permissions)
- Deployment pipelines beyond CI pre-check triggers

## User Roles

| Role | Abbreviation | Description |
|------|--------------|-------------|
| Engineering Manager | EM | Responsible for workspace setup, knowledge base generation, Full BMAD project planning, issue assignment, sprint metrics, post-deployment documentation, release coordination, and test management oversight |
| Agentic Delivery Engineer | ADE | Responsible for workspace setup, issue pickup, branching, spec creation, implementation, test framework setup, test generation and execution, commits, and pull request creation |

> Both EM and ADE roles share certain capabilities: workspace setup, context switching between issues/roles, committing changes, and test management (framework setup, test generation, execution, and coverage validation).

## Delivery Flows

The kit supports two primary delivery flows, each with its own branching model, planning depth, and handoff choreography. Bug remediation is a sub-flow within Full BMAD Projects, not a standalone delivery flow.

| Flow | Branch Model | Planning Depth | When to Use |
|------|-------------|---------------|-------------|
| M&O (feature/hotfix) Quick-Flow | 2-tier: `master` → `feature/*` or `hotfix/*` → `dev/*` | Change brief + Quick-Dev spec | Single-sprint enhancements, critical production fixes |
| Full BMAD Project | 3-tier: `master` → `project/*` (protected) → `feature/epic-*` → `dev/*` | Product brief → PRD → Architecture → Epics → Sprint plans → Story specs | Multi-sprint initiatives, new modules, large-scope work |

**Bug Remediation (Project sub-flow):** When defects are found during project testing (pre-release), bug branches are created from `project/*` or `feature/epic-*` (never from `master`). The **ADE** runs `/tdgs-aidlc-initiate-issue {bug_id} bug` after the EM logs the bug in GitHub; the ADE creates a bug brief and focused fix spec, following the same commit and PR conventions as the parent project.

**Workspace bootstrap:** `feature/initial-docs-setup` is a valid integration branch used once per application during initial docs/KB setup (see [setup.md](../setup.md)); it is not part of the M&O or Full BMAD delivery-flow rows above.

## Capability Area 1 — Workspace Setup and Infrastructure

Prompts: `quick-setup`, `setup-workspace`, `install-hooks`

### FR-1: Quick Setup and Upgrade

The kit provides a prompt that installs or upgrades the BMAD framework to the version specified in the workspace configuration and copies all AIDLC prompts, skills, and configuration templates into the workspace. An `update-workspace` mode re-scans repositories in the workspace and refreshes the worker-repo registry without altering existing configuration values.

### FR-2: Full Workspace Initialization

The kit provides a prompt for first-time workspace setup that creates the documentation repository structure, installs BMAD with the correct module selection, configures workspace settings, and registers all discovered repositories. The prompt detects the user's role (EM vs. ADE) and adapts its output accordingly.

### FR-3: Pre-Commit Hook Installation

The kit provides a prompt that installs Git pre-commit hooks across all registered worker repositories, including secret-scanning (Gitleaks) and conventional-commit enforcement. Hooks are installed idempotently and do not overwrite user-customized hook configurations.

### FR-4: Common Repository Integration

The kit supports two models for integrating shared/common service repositories:

**Symlinked Common Repos (Recommended):** Common service repositories are symlinked directly into the workspace and listed in `common_repos` in `i2a-config.yml`. Document Project scans them alongside worker repos and routes KB output to `knowledge-base/common-services/{key}/`. This model provides real-time access to common repo source code and eliminates manual sync steps.

**Legacy Reference Sync (Deprecated):** The kit provides a deprecated prompt (`reference-sync`) that synchronizes shared reference documentation from a designated common-services repository into the workspace's documentation repo. This model is retained for workspaces that cannot symlink common repos (e.g., different network locations, permission constraints).

| Model | Config Key | When to Use | KB Output Location |
|-------|------------|-------------|--------------------|
| Symlinked | `common_repos` | Default — repos can be symlinked into workspace | `knowledge-base/common-services/{key}/` |
| Legacy Sync | `common_services` | Repos cannot be symlinked (network/permission constraints) | `knowledge-base/common-services/` |

### FR-5: Prerequisite Verification

The quick-setup and workspace-initialization prompts verify that required tooling meets minimum version thresholds (Node.js v20+, Python 3.10+, uv, Git, VS Code with GitHub Copilot agent mode) before proceeding. Missing or outdated prerequisites produce actionable error messages with install instructions.

### FR-6: Configuration Template Management

The kit provides a workspace configuration template (`i2a-config.yml`) that defines the issues repository, worker repositories, common repositories (symlinked), and BMAD version. Sixteen of the thirty-three prompts read this configuration file at runtime to resolve repository paths, branch names, and version constraints.

## Capability Area 2 — Issue and Project Initiation

Prompts: `initiate-issue`, `initiate-project`, `show-available-stories`

### FR-7: M&O Issue Initiation

The kit provides a prompt that accepts a GitHub Issue ID and issue type (`feature` or `hotfix`), fetches the issue metadata, creates a 2-tier branch structure (`feature/*` or `hotfix/*` integration branch from `master`, plus a personal `dev/*` branch), and generates a change brief summarizing the work scope. The prompt validates that the docs repo is on the `master` branch and has a clean working tree before proceeding.

### FR-8: Full BMAD Project Initiation

The kit provides a prompt that accepts a GitHub Issue ID, creates a protected `project/*` branch and a companion `planning/*` branch from `master`, generates a change brief, and outputs the ordered sequence of BMAD planning skills the EM should invoke next. The prompt configures branch protection rules (via a CI guard workflow) that restrict direct pushes to the project branch to only `sprint-status.yaml` and `bug-brief-*.md` files.

### FR-9: Bug Issue Initiation

The kit provides a prompt that accepts a bug GitHub Issue ID with type `bug`, resolves the linked parent project issue, verifies the docs repo is on the correct `project/*` branch, and generates a bug brief containing reproduction steps, expected vs. actual behavior, and affected areas. Bug branches are created from the project or epic branch — never from `master`.

### FR-10: Available Story Discovery

The kit provides a prompt that reads the sprint status file, scans remote branches across all worker repositories for existing claims, evaluates inter-story dependencies for blocking conditions, and displays stories in categorized groups: AVAILABLE, BLOCKED, CLAIMED, and DONE. An optional epic filter narrows results to a single epic.

### FR-11: Collision Prevention for Story Claims

When an ADE runs the repository preparation prompt for a story that another ADE has already claimed (evidenced by an existing remote `dev/*` branch), the kit blocks the operation with an explicit error identifying the claiming user. Branch push serves as the atomic claim mechanism.

## Capability Area 3 — Development Workflow

Prompts: `prepare-repos`, `switch`, `commit`, `pre-check-pull-request`, `create-pull-request`

### FR-12: Repository Branch Preparation (M&O)

The kit provides a prompt that reads the change brief or spec to identify affected worker repositories, then creates integration and dev branches in each repository following the 2-tier M&O branch hierarchy. Existing branches trigger a skip/reset/abort choice.

### FR-13: Repository Branch Preparation (Project)

The kit provides a prompt that, given a story spec path, creates a 3-tier branch structure in each affected worker repository: project branch (from `master`, if not existing), epic branch (from project branch, if not existing), and story dev branch (from epic branch). Multiple stories in the same epic share the epic branch.

### FR-14: Repository Branch Preparation (Bug)

The kit provides a prompt that reads the fix spec and creates bug dev branches from the appropriate parent branch (project or epic), using the naming convention that encodes bug scope (project-level, epic-level, or story-level).

### FR-15: Context Switching

The kit provides a prompt that switches the workspace between different issues or between EM and ADE roles on the same issue. The prompt resolves the correct docs branch, switches all relevant worker repositories to matching branches, and preserves uncommitted changes via stash. A direct spec-path argument bypasses interactive story selection.

### FR-16: Conventional Commit Automation

The kit provides a prompt that stages changes, validates them against sensitive-file rules (blocking commits of `.env`, credentials, or token files), and generates a conventional commit message with the appropriate type prefix, scope, and description. The prompt reads the workspace configuration to discover repositories (from `worker_repos` and `common_repos`) and determine the commit scope from the current issue context.

### FR-17: CI Pipeline Pre-Check

The kit provides a prompt that reads the workspace configuration to discover repositories, triggers the CI pipeline on the current dev branch, monitors execution status, and reports pass/fail results. The prompt detects known Gitleaks baseline issues on `workflow_dispatch` triggers and warns the user proactively when the failure is a known limitation rather than a real secret leak.

### FR-18: Pull Request Creation

The kit provides a prompt that creates a GitHub Pull Request with a structured description (summary, changes, testing notes, reviewer checklist). The PR target branch is automatically determined from the current branch type: dev branches target their parent integration or epic branch. For bug branches, the target is derived from the branch naming convention (epic-level bugs target the epic branch; project-level bugs target the project branch).

### FR-19: Branch Naming Enforcement

All branch-creating prompts enforce the documented naming conventions, including kebab-case slugs derived from issue titles, maximum branch name length of 100 characters, and the `ghi-` prefix denoting GitHub Issue references. Branch names are validated against documented regex patterns before creation.

## Capability Area 4 — Test Management

Prompts: `setup-unit-tests`, `setup-api-tests`, `setup-functional-tests`, `setup-testdata`, `generate-unit-tests`, `generate-api-tests`, `generate-functional-tests`, `run-tests`

### FR-20: Unit Test Framework Setup

The kit provides a prompt that scaffolds the unit test infrastructure in a worker repository, configuring the appropriate test runner (Jest, JUnit, or pytest based on the project's technology stack) with coverage reporting and HTML dashboard generation.

### FR-21: API Test Framework Setup

The kit provides a prompt that scaffolds the API/integration test infrastructure, including Insomnia collection templates, environment configuration, and test-data catalog integration.

### FR-22: Functional Test Framework Setup

The kit provides a prompt that scaffolds the Playwright-based functional test infrastructure for UI repositories, including page-object models, flow descriptors, and mock/real execution modes.

### FR-23: Test Data Catalog Generation

The kit provides a prompt that discovers API chains, identity fields, and UI screens from the knowledge base and source code, then generates a structured test-data catalog (`test-data-catalog.yaml`) with API chain definitions, identity pools, UI screen mappings, and cross-service stub configurations. Identity pool records are initialized with placeholder sentinels that the user must populate with real test values. The catalog file is automatically added to `.gitignore` because it contains PII-shaped test data.

### FR-24: Unit Test Generation

The kit provides a prompt that discovers testable units from source code and generates hermetic tests (no catalog or network dependencies) with hard gates for exception paths, thread-safety, and exact assertions. Tests are generated per-module until the specified coverage threshold is met, followed by post-generation validation.

### FR-25: API Test Generation

The kit provides a prompt that discovers API endpoints from target services, generates Insomnia collections with catalog tokens, performs lint and audit checks, executes the tests, and produces coverage and result reports. The test-data catalog must exist before API test generation.

### FR-26: Functional Test Generation

The kit provides a prompt that enumerates UI flows from flow descriptors, generates Playwright spec files, and supports both mock and real execution modes. The prompt accepts optional filters for specific UI repositories, flow names, and coverage targets. The test-data catalog must exist before functional test generation.

### FR-27: Test Execution and Reporting

The kit provides a prompt that discovers repositories with test infrastructure, executes tests across all three layers (unit, API, functional), and generates consolidated reports including HTML dashboards, markdown summaries, and JSON result files. Tests can be scoped to the full suite or narrowed to files changed by the current issue. Results are classified as pass, fail, skip, data-issue, or infra, and pass rate excludes skipped tests.

### FR-28: Three-Layer Test Coverage Model

The kit enforces a three-layer testing strategy: unit tests (hermetic, per-module), API/integration tests (service-level, catalog-driven), and functional tests (end-to-end, Playwright-based). Each layer has independent setup, generation, and execution prompts, and all three contribute to the workspace test dashboard.

## Capability Area 5 — Sprint Management and Metrics

Prompts: `generate-dashboard`, `update-metrics`, `manage-blockers`, `metrics-report`, `project-course-correction`; Skill: `project-kanban-planning`

### FR-29: Sprint Dashboard Generation

The kit provides a prompt that generates a live HTML sprint dashboard from planning artifacts (epics, kanban plan, sprint status, sprint metrics). The dashboard auto-refreshes from the YAML status file at runtime (5-second polling interval) without requiring regeneration for daily status changes. Regeneration is only needed when the sprint structure changes (stories added, removed, or reorganized).

### FR-30: Sprint Metrics Updates

The kit provides a prompt that updates the sprint status file after a story status change. The prompt validates that the status transition is allowed (enforcing a defined state machine), calculates UTC timestamps, and computes Harvey ball quality metrics on a 0–4 scale. Both interactive and inline invocation modes are supported.

### FR-31: Blocker Management

The kit provides a prompt that adds, resolves, or updates blockers on stories in the sprint status file. Each blocker entry includes a summary, impact level, action needed, and resolution status. The dashboard reflects blocker state in real time via YAML polling.

### FR-32: Metrics Reporting

The kit provides a prompt that parses the sprint status file, calculates aggregate statistics (velocity, completion rate, blocker count, average cycle time), identifies attention items, and generates a formatted markdown report suitable for stakeholder communication.

### FR-33: Mid-Project Course Correction

The kit provides a prompt that accepts a change request from multiple sources (GitHub Issue comment, sub-issue, document, URL, or inline text), generates a change-request brief on the planning branch, delegates impact analysis to the BMAD correct-course skill, and presents the EM with approve/defer/reject options. Approved changes are applied to affected specs, stories, and kanban artifacts. In-progress stories receive an additive "Course Correction" section describing delta instructions; completed stories may trigger follow-up stories. The prompt commits changes and creates a PR from the planning branch to the project branch.

### FR-34: Sprint Status State Machine

Story statuses follow a defined lifecycle: `backlog` → `ready-for-dev` → `in-progress` → `review` → `done`. The metrics-update prompt enforces valid transitions and rejects invalid state changes. Timestamps are recorded at each transition for cycle-time calculation.

### FR-41: Kanban Planning Orchestration

The kit provides a prompt backed by a custom skill that checks prerequisites (PRD, architecture docs), delegates to BMAD `create-epics-and-stories` and `sprint-planning` skills if prerequisites are missing, parses epics for dependencies and complexity estimates, generates a kanban plan with dependency graph and prioritization, and triggers the sprint-dashboard skill for HTML generation. An `update` mode reloads parameters and skips directly to the planning phase.

## Capability Area 6 — Documentation and Knowledge Base

Prompts: `generate-kb`, `update-context-docs`, `validate-runbook-context`, `validate-test-context`, `post-deployment-docs-sync`, `ops-runbook`

### FR-35: Knowledge Base Synchronization (Project Mode)

The kit provides a prompt that, when run on a `project/*` branch, detects commits merged since the last sync, maps code changes to knowledge-base documents, performs exhaustive regeneration of affected sections from worker-repo source code, and records a sync timestamp in a metadata file. Changes are staged on the planning branch for review via PR.

### FR-36: Knowledge Base Synchronization (Release Mode)

The kit provides a prompt that, when run on a `release/*` branch, performs the same delta-scanning and regeneration workflow as project mode but scoped to release-specific changes.

### FR-37: Runbook Validation

The kit provides a prompt that extracts operational data from runbook markdown files, compares it against knowledge-base context documents across ten validation categories, and generates a deterministic validation report with categorized discrepancies.

### FR-38: Test Context Validation

The kit provides a prompt that extracts business rules from context documents, parses manual test cases and their expected values, compares test-case values against context-doc business rules, and generates a severity-categorized validation report.

### FR-39: Post-Deployment Documentation Sync

The kit provides a prompt that, after a production release, validates the release tag, identifies merged issues, prompts for Apigee documentation updates (skippable), creates a dedicated docs branch, invokes BMAD Document Project in update mode to regenerate knowledge-base content from worker repos, adds a deployment-history entry, and creates a PR to `master`. Flags support dry-run mode, forced re-sync, Apigee skip, and common-services sync.

### FR-40: Knowledge Base Freshness Fallback

When the sync metadata file is missing or corrupt (e.g., first sync on a project), the knowledge-base sync prompt falls back to full reconciliation mode, scanning all commits on the project branch since its fork from `master`. A new metadata file is created after the sync completes.

### FR-55: Ops Runbook Update and Create

The kit provides a prompt that updates an existing operational runbook (`.docx` or `.md`) for a release, or creates a new `.md` runbook from the Texas.gov Run Book Template. Update mode scopes edits to repositories listed in the implementation plan version matrix; Create mode generates a full template-aligned runbook with Mermaid architecture and sequence diagrams grounded in knowledge-base and source evidence. Both modes are application-agnostic, enforce exhaustiveness and anti-hallucination guardrails, and write only to the runbook output (workspace source and knowledge base remain read-only).

## Capability Area 7 — Custom Skills and BMAD Integration

Skills: `project-kanban-planning`, `sprint-dashboard`, `setup-api-tests`, `generate-api-tests`, `setup-unit-tests`, `generate-unit-tests`, `setup-functional-tests`, `generate-functional-tests`, `setup-testdata`, `ops-runbook`, `help`; BMAD dependency: 11 of 41 skills

### FR-42: Sprint Dashboard Skill

The kit provides a custom skill that parses epics, kanban plan, sprint status, and metrics files; builds a JavaScript configuration from the parsed data; and generates an HTML dashboard with KPIs, charts, Harvey ball quality indicators, blocker tracking, and critical-path visualization. The skill also provides sub-workflows that back the `update-metrics`, `manage-blockers`, and `metrics-report` prompts.

### FR-43: BMAD Skill Delegation

The kit delegates to BMAD skills for capabilities outside its own scope. One AIDLC prompt (`project-course-correction`) directly invokes a BMAD skill (`bmad-correct-course`) during execution. One AIDLC custom skill (`project-kanban-planning`) directly invokes two BMAD skills (`bmad-create-epics-and-stories`, `bmad-sprint-planning`). Nine additional BMAD skills are recommended as next steps in prompt output messages but are not invoked programmatically.

### FR-44: BMAD Version Pinning

The kit pins its BMAD dependency to a specific version (currently 6.3.0) in the workspace configuration file. The quick-setup and workspace-initialization prompts install exactly that version. Upgrading requires updating the pinned version and verifying compatibility using the upgrade impact matrix documented in the ACE catalog.

### FR-45: Skill Installation Separation

AIDLC custom skills are installed to a dedicated directory (`.github/i2a-skills/`) separate from BMAD skills (`.github/skills/`), preventing version conflicts and enabling independent upgrade cycles for each skill set.

### FR-46: API Test Framework Skill

The kit provides a custom skill that scaffolds per-service API test infrastructure (Insomnia collections, environment configurations, test runner, report generator, collection linter, and coverage auditor). The skill ships reference implementation templates and a pinned runner output contract that defines the `results.json` schema, status enum, math invariant, and exit code semantics for downstream CI/CD consumers. The collection linter enforces 12 rules (LINT-1 through LINT-12) covering assertion methods, token grammar, JSON validity, attack-payload detection, PII-name detection, and catalog-token usage.

### FR-47: API Test Generation Skill

The kit provides a custom skill that orchestrates API test generation through a two-phase discovery workflow (knowledge-base OpenAPI scan followed by source-code endpoint scan), a pre-write output contract gate (9 validation blocks), 25 guardrails (G1 through G25) covering application-agnostic generation, PII handling, and chain wiring, and a post-generation mechanical gate (20 automated checks). The skill produces Insomnia collections organized by test category (positive, negative, edge-case, security, contract), executes them via the test runner, and generates HTML reports, markdown summaries, JSON result files, and data ledgers. A field derivation hierarchy (P0 through P6 provenance tiers) governs value resolution for request payloads.

### FR-48: Unit Test Framework Skill

The kit provides a custom skill that auto-detects the project's technology stack (Java/Maven/Gradle, JavaScript/TypeScript with Jest/Vitest, Python/pytest, .NET/xUnit) and scaffolds per-repository unit test infrastructure with appropriate coverage tooling, `generate-report.js` stubs, `coverage.json` configuration, and `TESTING.md` documentation. The skill includes six tool documents covering stack-specific scaffolding (Java, JavaScript, other stacks), preflight discovery, guardrails, and execution verification. Generated scaffolds are hermetic by design (no test-data catalog dependency).

### FR-49: Unit Test Generation Skill

The kit provides a custom skill that orchestrates unit test generation through knowledge-base and source-code discovery, a pre-write output contract (U1–U3), 8 guardrails governing hermeticity (no catalog or network dependencies), exception path coverage, and exact assertions, and 8 post-generation mechanical checks. The skill generates tests per-module until a specified coverage threshold is met, supporting JaCoCo, Jest, Vitest, pytest, and Coverlet reporting frameworks.

### FR-50: Functional Test Framework Skill

The kit provides a custom skill that scaffolds the Playwright-based functional test infrastructure in UI repositories, including Playwright configuration, page-object models, fixtures (`api-mock.js`, catalog fixture, flow-runner), component detection helpers (react-select, datepicker, wizard), flow descriptors, and `generate-report.js` stubs. The skill includes eight tool documents covering scaffold structure, component detection, fixtures, flow descriptors, guardrails, Playwright configuration, preflight discovery, and verification with documentation generation. Scaffolds are idempotent and safe to re-run.

### FR-51: Functional Test Generation Skill

The kit provides a custom skill that orchestrates Playwright functional test generation through multi-phase discovery (flow descriptors, knowledge base, source code), a pre-write contract (F1–F6), gap analysis, 14+ post-generation checks plus a Standards Audit Script, and execution with HTML/markdown/ledger reports. The skill supports both mock and real execution modes and generates spec files organized by flow, test-case, and persona matrix.

### FR-54: Test Data Catalog Skill

The kit provides a custom skill that orchestrates test-data catalog generation through a 5-step pipeline: project-context validation, multi-phase discovery (endpoint scanning, API chain detection, UI screen mapping, identity pool classification), interactive data collection with workbook import support, catalog YAML generation with idempotent merge semantics, and dashboard script generation with JSON Schema contracts. The skill enforces 13 guardrails (G1–G13) covering application-agnostic generation, discover-before-generate ordering, ask-don't-assume identity handling, PII safety (catalog gitignored), cross-service stub canonicalization, pre-write output contracts, and shared math invariants. A field derivation hierarchy (P0–P6 provenance tiers) governs value resolution for catalog entries. The skill includes 8 tool documents (guardrails, ground-truth hierarchy, discovery, data collection, catalog generation, dashboard generation, ledger/schemas, hard rules) and sits in the test pipeline between framework setup and test generation.

### FR-56: Ops Runbook Skill

The kit provides a custom skill that backs the ops-runbook prompt with dual-mode dispatch: Update (`workflow.md`) for release-scoped surgical edits to existing `.docx` or `.md` runbooks, and Create (`workflow-create.md`) for new `.md` runbooks from the Texas.gov template. The skill ships organization defaults (`config/org-defaults.yaml`), create-mode guardrails and section grounding rules, diagram standards, post-generation checks, a runbook markdown template, Mermaid-to-SVG rendering (`scripts/render-diagrams.sh`), and optional UI screenshot capture (`scripts/capture-screenshots.js`). Update mode enforces format-preserving `.docx` edits (python-docx, backup/rollback, placement gates); Create mode requires evidence-table-backed diagrams and operational voice suitable for on-call use.

## Capability Area 8 — Help and Reference

Prompts: `help`

### FR-52: Interactive Command Reference

The kit provides a read-only prompt that surfaces the complete AIDLC prompt and skill catalog without modifying files. The prompt supports four response modes: (1) no argument displays a full at-a-glance catalog of all 33 prompts and 11 skills grouped by functional area with model-complexity indicators, (2) a prompt or skill name shows targeted details (syntax, inputs, what it does, prerequisites, examples, next steps), (3) a free-text goal or question maps to the appropriate command(s) with usage guidance, and (4) the `workflows` keyword shows end-to-end workflow sequences for common scenarios. Name matching is flexible — users can omit the `tdgs-aidlc-` prefix, and partial matches show all candidates.

### FR-53: Help Skill Reference Data

The kit provides a custom skill that backs the help prompt with two reference-data files: a full per-prompt catalog (`tools/catalog-data.md`) containing syntax, inputs, examples, prerequisites, and next steps for every AIDLC command, and a workflow-sequences file (`tools/workflow-sequences.md`) containing end-to-end command sequences for seven common scenarios (first-time setup, M&O dev cycle, project lifecycle, testing pipeline, sprint management, post-deployment, and role-based quick reference).

## Non-Functional Requirements

### NFR-1: Portability

The kit's internal test suite and automation scripts have zero npm runtime dependencies. All test suites run on Node.js 20+ using only built-in modules (`fs`, `path`, `assert`). The kit operates in any multi-repository VS Code workspace without requiring a specific operating system, shell, or container runtime.

### NFR-2: Extensibility

The kit follows documented patterns for adding new prompts, custom skills, user guides, and test suites. The ACE catalog provides a complete dependency graph, upgrade impact matrix, and configuration-consumer map. New prompts follow the established naming convention (`tdgs-aidlc-{verb}-{noun}`) and are automatically discovered by the test inventory suite.

### NFR-3: Quality Assurance

Eight automated test suites with 1884 checks validate the kit's structural integrity, cross-reference correctness, content quality, and behavioral rules:

| Suite | Validates |
|-------|-----------|
| Prompt Structure | Markdown structure, required sections, metadata consistency |
| Inventory | All prompts and skills are registered and discoverable; unexpected file detection |
| Cross-References | Internal links between docs, prompts, and guides resolve correctly; skill internal file references |
| Content Quality | Writing standards, heading hierarchy, placeholder absence |
| Guide Structure | User-guide completeness and structural consistency |
| Workflow Completeness | End-to-end workflow coverage across all delivery flows |
| Version Consistency | Version strings match across README, config, changelog, and prompts; NEXT_VERSION format validation |
| Simulation | Behavioral rules and prompt interaction patterns |

All suites are included in the `npm test` CI gate and must pass before any release.

### NFR-4: Compatibility

The kit requires VS Code with GitHub Copilot agent mode enabled. MCP servers (Splunk, database) are optional and enhance capabilities but are not required for core workflows. The kit is tested against Node.js 20+ and Python 3.10+. Git is required for all branching and commit operations.

### NFR-5: Configuration Isolation

Workspace configuration (`i2a-config.yml`) is scoped to the individual workspace instance. The kit does not read from or write to global user-level or system-level configuration files. Multiple workspaces on the same machine operate independently.

### NFR-6: Idempotency

Setup and installation prompts (quick-setup, setup-workspace, install-hooks) are idempotent. Running them multiple times produces the same end state without duplication, data loss, or configuration corruption. Prompts that create branches handle the "branch already exists" case gracefully with skip/reset/abort options.

### NFR-7: Secret Safety

The commit prompt blocks staging of files matching sensitive-file patterns (`.env`, credentials, tokens). Pre-commit hooks include Gitleaks secret scanning. The test-data catalog is automatically added to `.gitignore` to prevent accidental commit of PII-shaped test data.

### NFR-8: CI/CD Integration

The kit includes GitHub Actions workflows for continuous integration. The `release` workflow runs `npm test` as part of the release pipeline. The `project-branch-guard` workflow restricts direct pushes to protected `project/*` branches. CI pre-check prompts trigger pipeline execution and report results within the IDE.

### NFR-9: User-Controlled Version Override

The release workflow supports an optional version override via a `NEXT_VERSION` file in the repository root. When `NEXT_VERSION` contains a valid semver string (X.Y.Z) that is strictly greater than the auto-incremented version, the release uses that value instead. After each release, the workflow clears `NEXT_VERSION` and commits the empty file, ensuring the override is consumed exactly once. If `NEXT_VERSION` is empty, missing, contains an invalid format, or holds a version not greater than the auto-incremented value, the workflow falls back to the standard auto-increment logic. This allows users to control version jumps (e.g., for major releases) by writing the desired version into `NEXT_VERSION` before merging to `master`.

## User Workflows

### Workflow 1: M&O Feature Delivery (ADE)

An ADE picks up a feature issue assigned by the EM and delivers it through the M&O Quick-Flow.

1. **Initiate** — Run `initiate-issue` with the issue ID and type `feature` to create branches and generate the change brief
2. **Commit docs** — Run `commit` to save the change brief, then `create-pull-request` for the docs repo
3. **Prepare worker repos** — Run `prepare-repos` to create integration and dev branches in affected worker repositories
4. **Implement** — Invoke the BMAD `quick-dev` skill to create the spec, implement, and self-review
5. **Code review** — Invoke the BMAD `code-review` skill for adversarial review
6. **Test** — Run `generate-unit-tests` and/or `run-tests` to validate the implementation
7. **Commit and PR** — Run `commit`, then `pre-check-pull-request` to validate CI, then `create-pull-request` to open the PR targeting the integration branch
8. **Notify EM** — Hand off for release coordination

### Workflow 2: Full BMAD Project (EM + ADE)

An EM plans a multi-sprint initiative and hands off stories to ADEs for implementation.

**EM Planning Phase:**

1. **Initiate project** — Run `initiate-project` with the issue ID to create protected project and planning branches
2. **BMAD planning** — Invoke `bmad-product-brief`, `bmad-create-prd`, `bmad-create-architecture`, `bmad-create-epics-and-stories`, and `bmad-sprint-planning` in sequence
3. **Kanban planning** — Run the `project-kanban-planning` skill to generate the kanban board and sprint dashboard
4. **Story specs** — Invoke `bmad-create-story` for each story in the current sprint
5. **Commit and PR** — Run `commit` and `create-pull-request` to merge planning artifacts from the planning branch to the project branch

**ADE Implementation Phase (per story):**

1. **Discover stories** — Run `show-available-stories` to see unclaimed, unblocked work
2. **Initiate issue** — Run `initiate-issue` with the project issue ID and type `project`
3. **Prepare repos** — Run `prepare-repos` with the story spec path to create 3-tier branches
4. **Implement** — Invoke the BMAD `dev-story` skill
5. **Review, test, commit, PR** — Same as M&O steps 5–7, but PRs target the epic branch

### Workflow 3: Bug Remediation within a Project (ADE)

An ADE fixes a defect discovered during project testing. This is a sub-flow of the Full BMAD Project, not a standalone delivery flow.

1. **Initiate bug** — Run `initiate-issue` with the bug issue ID and type `bug` to generate the bug brief
2. **Fix spec** — Invoke the BMAD `quick-dev` skill with bug context to produce a focused fix spec
3. **Prepare repos** — Run `prepare-repos` to create bug branches from the parent project or epic branch
4. **Implement and PR** — Implement the fix, commit, and create a PR targeting the parent branch

### Workflow 4: Sprint Dashboard Management (EM)

An EM tracks sprint progress and reports to stakeholders.

1. **Generate dashboard** — Run `generate-dashboard` to create the initial HTML dashboard
2. **Update metrics** — Run `update-metrics` after each story status change to record timestamps and Harvey ball scores
3. **Manage blockers** — Run `manage-blockers` to add, resolve, or update blockers as they arise
4. **Generate report** — Run `metrics-report` to produce a stakeholder-ready markdown summary
5. **Course correct** — Run `project-course-correction` when a mid-sprint change request arrives

### Workflow 5: Post-Deployment Sync (EM)

An EM synchronizes the knowledge base after a production release.

1. **Confirm deployment** — Verify the release tag exists and the deployment succeeded
2. **Run sync** — Run `post-deployment-docs-sync` with the release version to regenerate KB content
3. **Review and merge** — Review the generated PR and merge to `master`

| **AIDLC** | AI-Assisted Development Lifecycle — the methodology and toolkit for AI-driven software delivery within TDGS |

| **Bug Brief** | A summary document generated during bug initiation that captures reproduction steps, expected vs. actual behavior, affected areas, and linked project context |
| **Course Correction** | A mid-project change request that modifies planning artifacts, story specs, or sprint scope; managed through the `project-course-correction` prompt |
| **Dev Branch** | A personal working branch (`dev/*`) where an individual ADE implements a story, feature, or bug fix |
| **Docs Repo** | The documentation repository in the workspace that holds planning artifacts, knowledge base, sprint status, and implementation artifacts |

| **Full BMAD** | The complete BMAD planning workflow (product brief → PRD → architecture → epics → sprint planning → story specs) used for multi-sprint projects |
| **Harvey Ball** | A 0–4 quality metric scale used in sprint status to rate story completion quality (0 = not started, 4 = exceptional) |
| **i2a-config.yml** | The workspace configuration file that registers the issues repository, worker repositories, common services, and BMAD version |
| **I2A Team** | The Innovation to Automation team within TDGS that maintains the AIDLC Starter Kit |
| **Integration Branch** | A `feature/*`, `hotfix/*`, or `project/*` branch that serves as the merge target for dev branch PRs. **Setup exception:** `feature/initial-docs-setup` (created during workspace/KB bootstrap) is an integration branch even though it is not listed in the delivery-flow table above. |
| **Knowledge Base (KB)** | Generated documentation in the docs repo that captures API specs, business rules, architecture, and technology stack from worker-repo source code |
| **M&O** | Maintenance and Operations — the Quick-Flow delivery model for single-sprint features and hotfixes |
| **MCP** | Model Context Protocol — a protocol for connecting AI agents to external data sources (Splunk, databases); optional in AIDLC |
| **Planning Branch** | A `planning/*` branch where the EM performs Full BMAD planning work before merging to the project branch via PR |
| **Project Branch** | A protected `project/*` branch that serves as the integration point for a Full BMAD project; code changes require PRs |
| **Quick-Dev** | A BMAD skill (`/bmad-quick-dev`) that creates a spec, implements, and self-reviews in a single workflow; used in M&O and bug-fix flows |
| **Quick-Flow** | The streamlined M&O delivery workflow using 2-tier branching and `quick-dev` for spec + implementation |
| **Sprint Dashboard** | A live HTML dashboard that displays KPIs, story statuses, Harvey ball metrics, blocker state, and critical path; auto-refreshes from YAML |
| **Sprint Status** | A YAML file (`sprint-status.yaml`) that tracks story statuses, timestamps, metrics, blockers, and dependencies for a project sprint |
| **Story Spec** | An implementation-ready specification file for a single user story, produced by the BMAD `create-story` skill during project planning |
| **TDGS** | Texas.gov Digital Government Services — the program under which the AIDLC Starter Kit operates |
| **Test-Data Catalog** | A YAML file that defines API chains, identity pools, UI screen mappings, and cross-service stubs used by API and functional test generators |
| **Worker Repo** | A code repository (UI, service, library) that is registered in the workspace configuration and targeted by branch-creation and implementation prompts |
| **Guardrails** | Numbered non-negotiable constraints (G1–G13) embedded in skill tools that govern agent behavior — e.g., G1 (application-agnostic), G3 (ask-don't-assume), G9 (idempotent merge). Different from the colloquial meaning of "safety rails" |
| **Pre-flight Check** | A mandatory diagnostic step at the start of a prompt that verifies the workspace is a multi-repo workspace, identifies repository directories, and BAILs with an error message if the environment is not suitable |
| **Persona** | The `em` or `ade` parameter passed to `setup-workspace` and `switch` to configure the workspace for an Engineering Manager or Agentic Delivery Engineer role |
| **Coverage Target** | The `coverage_target` parameter (default 80%) passed to test generation prompts specifying the minimum code coverage threshold for generated tests |
| **Flow Descriptor** | A structured YAML or Markdown file describing a user flow (screen sequence, assertions, test data) consumed by the functional test generator during Phase 0a discovery |
| **Kanban Plan** | The output artifact of the `project-kanban-planning` skill: a structured document with dependency graph, prioritized story order, and sprint allocation used to drive the sprint dashboard |
