# /tdgs-aidlc-prepare-repos

Prepare worker repositories for development by creating feature branches in all code repositories affected by the spec.

## Pre-flight Check: Multi-Repository Workspace

> ⚠️ **CRITICAL**: The workspace root is NOT a git repository. Git repositories are located in subdirectories within the workspace.
>
> **DO NOT** run `git` commands at the workspace root level — they will fail.
>
> **ALWAYS** identify individual repository directories (from `worker_repos` config) first, then run git commands within those directories.

---

## Inputs

| Input | Source | Required |
|-------|--------|----------|
| Spec File | User-provided path OR auto-detected `spec-*.md` | Yes |
| Current Branch | Git (docs repo) | Yes |
| Worker Repos | `.github/i2a-config.yml` → `worker_repos` + `common_repos` | Yes |

### Spec File Resolution

- **If a spec file path is provided** (e.g., `/tdgs-aidlc-prepare-repos implementation-artifacts/1-1-project-scaffolding.md`): use that file directly
- **If no path provided**: auto-detect by looking for `{docs}/implementation-artifacts/spec-*.md`
- **If no spec file found and change-brief `issue_type` is `project`**: → **BAIL** — story spec path is required for project workflow:
  ```
  ❌ No spec file found

  This is a project workflow (issue_type: project).
  You must specify which story spec to use:

    /tdgs-aidlc-prepare-repos {story-spec-file}

  Available story specs in implementation-artifacts/:
    - 1-1-project-scaffolding-and-configuration-foundation.md
    - 1-2-exception-hierarchy-and-global-error-handler.md
    ...

  Example:
    /tdgs-aidlc-prepare-repos implementation-artifacts/1-1-project-scaffolding-and-configuration-foundation.md
  ```

## Execution Steps

### 1. Pre-flight Checks
- Confirm current branch follows an accepted pattern:
  - **M&O workflow**: `dev/ghi-{issue_id}-{slug}-{username}` (docs repo on dev branch)
  - **Project workflow**: `project/ghi-{issue_id}-{slug}` (docs repo stays on project branch)
  - **Bug workflow**: `project/ghi-{issue_id}-{slug}` (docs repo stays on project branch; bug-brief exists)
- **Determine workflow type from branch**:
  - If on `dev/ghi-*`: M&O workflow — parse integration branch from dev branch name
    - Extract `feature/ghi-{issue_id}-{slug}` or `hotfix/ghi-{issue_id}-{slug}` (check change-brief for type)
    - Example: `dev/ghi-123-zip-fix-johndoe` → integration branch is `feature/ghi-123-zip-fix`
  - If on `project/ghi-*`: Project or Bug workflow — the current branch IS the integration branch
    - Extract `{issue_id}` and `{slug}` from branch name
    - **Detect bug workflow**: If spec file is a bug-brief (`bug-brief-*.md`) OR if a `planning-artifacts/bug-brief-{id}.md` matches the provided spec, this is a bug workflow
- **Resolve spec file** using the Spec File Resolution rules above
  - For bug workflow: spec is `planning-artifacts/bug-brief-{bug_id}.md` or a fix spec generated by `/bmad-quick-dev` (e.g., `implementation-artifacts/spec-bug-{slug}.md`)
- Load worker repos from `.github/i2a-config.yml`
- **Read change-brief or bug-brief** to get issue type (`feature`, `hotfix`, `project`, or `bug`) for branch naming
- **If project type**: Parse the story spec filename to extract `{epic_number}` and `{story_number}` (e.g., `1-1-project-scaffolding...md` → epic=1, story=1). Also read epic title from `planning-artifacts/epics.md` to derive the epic slug.
- **If bug type**: Read `bug-brief-{bug_id}.md` to determine:
  - `parent_project` (pid) and `project_branch`
  - `bug_scope` (project, epic, or story)
  - `epic_number` and `story_number` (if scoped to epic/story)
  - The parent branch from which to create the bug dev branch

### 2. Parse Spec for Affected Repositories

Read the spec and identify which repositories are affected. Look for:
- **Stories section** — Stories are typically organized by repository
- **Affected Services/Components section** — May explicitly list affected repos
- **Implementation sections** — Code changes indicate which repos need work

Map semantic names to repository keys dynamically:
1. Read all `worker_repos` and `common_repos` keys from `.github/i2a-config.yml` (merge both sections into a single lookup list)
2. For each service/component referenced in the spec, match to the closest key by suffix or semantic similarity (e.g., "Order Service" → `order-service`, "Frontend App" → `ui`)
3. If a spec reference cannot be confidently mapped to a config key, proceed to Step 2a (validation will catch it)
4. **Track which matched repos come from `common_repos`** — these are shared repos

### 2a. Validate Repositories Against Config

After identifying affected repositories from the spec, cross-reference them against `worker_repos` and `common_repos` in `.github/i2a-config.yml`. If ANY semantic name referenced in the spec cannot be mapped to a config key:

**For Project workflow (on `project/*` branch):**
```
⚠️  Spec references '{semantic_name}' but not found in i2a-config.yml worker_repos.

To add:
  1. Create the repository (if it doesn't exist yet)
  2. Clone it into the workspace
  3. Switch docs to planning/* branch
  4. Add to .github/i2a-config.yml → worker_repos
  5. Commit + PR to project/*
  6. After merge, re-run /tdgs-aidlc-prepare-repos {story-spec}
```

**For M&O workflow (on `dev/*` branch):**
```
⚠️  Spec references '{semantic_name}' but not found in i2a-config.yml worker_repos.

To add:
  1. Create the repository (if it doesn't exist yet)
  2. Clone it into the workspace
  3. Create a feature branch in docs repo from master
  4. Add to .github/i2a-config.yml → worker_repos
  5. Commit + PR to master
  6. After merge, re-run /tdgs-aidlc-prepare-repos
```

**Behavior:**
- Emit one warning per unresolved repo reference
- After listing all warnings, **STOP** — do NOT proceed to branch creation
- See [Adding Repositories to Workspace After KB Creation](../../doc/setup.md#adding-repositories-to-workspace-after-kb-creation) for the full process including KB generation

### 4. Create Branches

Branch creation differs based on issue type:
- **M&O (feature/hotfix)**: 2-tier — integration branch + dev branch
- **Project**: 3-tier — project branch + epic branch + dev branch
- **Bug**: 1-tier — dev branch from existing parent (project or epic branch)

---

#### M&O Workflow (feature/hotfix): 2-Tier Branching

For each affected repository:
1. Navigate to the repository folder in the workspace
2. Fetch latest from origin
3. **Create integration branch from master** (if not exists):
   - Checkout master and pull latest
   - Create `{type}/ghi-{issue_id}-{slug}` from master
   - Push integration branch to origin
4. **Create dev branch from integration branch**:
   - Create `dev/ghi-{issue_id}-{slug}-{username}` from integration branch
   - Push dev branch to origin
5. Checkout dev branch for work

##### 4a. Check and Create Integration Branch

**PowerShell (Windows):**
```powershell
cd {repo_path}
git fetch origin

$integrationExists = git branch -r 2>$null | Select-String "origin/{type}/ghi-{issue_id}-{slug}"

if (-not $integrationExists) {
    Write-Host "⚠ Integration branch not found. Creating from master..."
    git checkout master
    git pull origin master
    git checkout -b {type}/ghi-{issue_id}-{slug}
    git push -u origin {type}/ghi-{issue_id}-{slug}
    Write-Host "✓ Created integration branch {type}/ghi-{issue_id}-{slug}"
} else {
    git checkout {type}/ghi-{issue_id}-{slug}
    git pull origin {type}/ghi-{issue_id}-{slug}
}
```

**Bash (macOS / Linux):**
```bash
cd {repo_path}
git fetch origin

if ! git branch -r 2>/dev/null | grep -q "origin/{type}/ghi-{issue_id}-{slug}"; then
    echo "⚠ Integration branch not found. Creating from master..."
    git checkout master
    git pull origin master
    git checkout -b {type}/ghi-{issue_id}-{slug}
    git push -u origin {type}/ghi-{issue_id}-{slug}
    echo "✓ Created integration branch {type}/ghi-{issue_id}-{slug}"
else
    git checkout {type}/ghi-{issue_id}-{slug}
    git pull origin {type}/ghi-{issue_id}-{slug}
fi
```

##### 4b. Create Dev Branch

**PowerShell (Windows):**
```powershell
git checkout -b dev/ghi-{issue_id}-{slug}-{username}
git push -u origin dev/ghi-{issue_id}-{slug}-{username}
Write-Host "✓ Created dev branch dev/ghi-{issue_id}-{slug}-{username}"
```

**Bash (macOS / Linux):**
```bash
git checkout -b dev/ghi-{issue_id}-{slug}-{username}
git push -u origin dev/ghi-{issue_id}-{slug}-{username}
echo "✓ Created dev branch dev/ghi-{issue_id}-{slug}-{username}"
```

**IMPORTANT**: Worker repo integration branches are created from master, and dev branches are created from integration branches. This ensures all development work is properly isolated and can be merged to the integration branch for testing.

#### Project Workflow: 3-Tier Branching

> **Branch hierarchy**: `master → project/* (protected) → feature/* (epic) → dev/* (story)`
>
> **Planning hierarchy**: `project/* → planning/* (EM planning, merged via PR to project/*)`

The project branch (`project/ghi-{issue_id}-{slug}`) is a **protected** integration branch — no direct pushes allowed. EM planning artifacts are merged into it via PR from the `planning/*` branch. The epic-level `feature/*` branch groups all stories within an epic, and each story gets its own `dev/*` branch.

**Naming patterns:**
| Tier | Pattern | Example |
|------|---------|--------|
| Project (exists) | `project/ghi-{issue_id}-{slug}` | `project/ghi-10-bulk-refund-application` |
| Epic | `feature/ghi-{issue_id}-epic-{N}-{epic_slug}` | `feature/ghi-10-epic-1-batch-submission-dry-run` |
| Story (dev) | `dev/ghi-{issue_id}-{N}-{S}-{story_slug}-{username}` | `dev/ghi-10-1-1-project-scaffolding-yogenjos` |

Where:
- `{N}` = epic number (from story spec filename, e.g., `1` from `1-1-...`)
- `{S}` = story number within epic (e.g., `1` from `1-1-...`)
- `{epic_slug}` = kebab-case of epic title from `epics.md` (truncated to ~40 chars)
- `{story_slug}` = story portion of the spec filename slug (e.g., `project-scaffolding` from `1-1-project-scaffolding-and-configuration-foundation.md`; truncate long slugs)
- `{username}` = ADE's GitHub username

For each affected repository:
1. Navigate to the repository folder
2. Fetch latest from origin
3. **Check project branch exists** (already created by EM or earlier prepare-repos run)
4. **Create epic branch from project branch** (if not exists):
   - Checkout project branch
   - Create `feature/ghi-{issue_id}-epic-{N}-{epic_slug}` from project branch
   - Push epic branch to origin
5. **Create dev branch from epic branch**:
   - Create `dev/ghi-{issue_id}-{N}-{S}-{story_slug}-{username}` from epic branch
   - Push dev branch to origin
6. Checkout dev branch for work

##### 4b. Check for Competing Claims (Self-Service Collision Prevention)

> **Purpose**: Prevent two ADEs from claiming the same story. A remote `dev/*` branch for the same story by a different user = already claimed.

Before creating branches, scan ALL worker repos for existing dev branches matching this story:

**PowerShell (Windows):**
```powershell
$storyPattern = "dev/ghi-{issue_id}-{N}-{S}-"
$myBranch = "dev/ghi-{issue_id}-{N}-{S}-{story_slug}-{username}"

$existingClaims = git branch -r 2>$null | Select-String "origin/$storyPattern"

foreach ($claim in $existingClaims) {
    $branchName = $claim.ToString().Trim() -replace "^origin/", ""
    if ($branchName -ne $myBranch) {
        $otherUser = ($branchName -split "-")[-1]
        Write-Host "⛔ ABORT: Story {N}-{S} already claimed by $otherUser"
        Write-Host "   Branch exists: origin/$branchName"
        break
    }
}
```

**Bash (macOS / Linux):**
```bash
STORY_PATTERN="dev/ghi-{issue_id}-{N}-{S}-"
MY_BRANCH="dev/ghi-{issue_id}-{N}-{S}-{story_slug}-{username}"

git branch -r 2>/dev/null | grep "origin/$STORY_PATTERN" | while read -r claim; do
    branch_name=$(echo "$claim" | sed 's/^ *origin\///')
    if [ "$branch_name" != "$MY_BRANCH" ]; then
        other_user=$(echo "$branch_name" | rev | cut -d- -f1 | rev)
        echo "⛔ ABORT: Story {N}-{S} already claimed by $other_user"
        echo "   Branch exists: origin/$branch_name"
        break
    fi
done
```

**If a competing claim is found → ABORT immediately:**
```
⛔ ABORT: Story {N}-{S} already claimed

Another ADE has already claimed this story:
  Branch: origin/dev/ghi-{issue_id}-{N}-{S}-{story_slug}-{other_user}
  Claimed by: {other_user}

This story is no longer available for pickup.

Run /tdgs-aidlc-show-available-stories to see what's free.
```
STOP execution — do NOT create any branches.

**If no competing claim found** → proceed to epic branch creation.

**Note:** This check runs against ALL worker repos before creating ANY branches. If a claim is found in even one repo, the entire operation aborts.

##### 4e. Update Sprint Status (Project Workflow Only)

After ALL worker repo branches are successfully created, update `sprint-status.yaml` in the docs repo:

1. Navigate to the docs repository
2. Ensure on the `project/*` branch
3. In `implementation-artifacts/sprint-status.yaml`, change the story status from `ready-for-dev` to `in-progress`
4. Update `last_updated` to today's date
5. Commit and push the change

```bash
cd {docs_repo_path}

# Update sprint-status.yaml — set story to in-progress
# Change: {N}-{S}-{story_slug}: ready-for-dev → {N}-{S}-{story_slug}: in-progress
# Also update: last_updated: {today's date}

git add implementation-artifacts/sprint-status.yaml
git commit -m "chore: mark story {N}-{S} as in-progress"
git push origin project/ghi-{issue_id}-{slug}
echo "✓ Updated sprint-status.yaml — story {N}-{S} now in-progress"
```

**If sprint-status update fails** (e.g., merge conflict from parallel ADE):
```
⚠ Failed to update sprint-status.yaml
  Branches were created successfully — the story IS claimed via dev/* branches.
  Sprint status will need manual sync.
  
  To fix: pull latest, resolve conflict, push again.
```
This is non-fatal — branch creation (the true claim) already succeeded.

**IMPORTANT**: In the project workflow, the merge flow is: `planning/* → project/* (planning complete) → dev/* → feature/* (epic) → project/* → master`. EM planning artifacts are merged to project/* via PR from planning/*. PRs from dev branches target the epic branch. Epic branches are merged to the project branch when the epic is complete.

#### Bug Workflow: Branch from Parent (Project/Epic)

> **Branch hierarchy**: Bug branches are created from the appropriate parent branch based on scope — NOT from master.
>
> Bug dev branches follow the M&O-like quick-flow but branch from `project/*` or `feature/*` (epic) instead of `master`.

**Naming patterns:**
| Scope | `{scope_prefix}` | Dev Branch Pattern | Parent Branch | PR Target |
|-------|-------------------|--------------------|---------------|-----------|
| Project (cross-epic) | _(empty)_ | `dev/ghi-{bug_id}-bug-{slug}-{username}` | `project/ghi-{pid}-*` | `project/ghi-{pid}-*` |
| Epic | `e{N}-` | `dev/ghi-{bug_id}-bug-e{N}-{slug}-{username}` | `feature/ghi-{pid}-epic-{N}-*` | `feature/ghi-{pid}-epic-{N}-*` |
| Story | `e{N}-s{S}-` | `dev/ghi-{bug_id}-bug-e{N}-s{S}-{slug}-{username}` | `feature/ghi-{pid}-epic-{N}-*` | `feature/ghi-{pid}-epic-{N}-*` |

**Validation regex:**
```regex
^dev\/ghi-\d+-bug-(e\d+(-s\d+)?-)?[a-z0-9]([a-z0-9-]*[a-z0-9])?-[a-z0-9]+$
```

**Length limit**: 100 chars max. Slug capped at 50 chars (truncate at word boundary).

For each affected repository:
1. Navigate to the repository folder
2. Fetch latest from origin
3. **Determine parent branch based on bug scope**:
   - **Project-level**: Use `project/ghi-{pid}-{slug}` as parent
   - **Epic-level or Story-level**: Use `feature/ghi-{pid}-epic-{N}-*` as parent
   - Verify parent branch exists on remote → BAIL if not found
4. **Checkout parent branch and pull latest**
5. **Create bug dev branch from parent**:
   - Create the appropriate `dev/ghi-{bug_id}-bug-*` branch
   - Push to origin
6. Checkout dev branch for work

##### Bug Branch Creation

**Bash (macOS / Linux):**
```bash
cd {repo_path}
git fetch origin

# Determine parent branch (from bug-brief metadata)
PARENT_BRANCH="{parent_branch}"  # e.g., project/ghi-10-bulk-refund or feature/ghi-10-epic-1-batch-submission

if ! git branch -r 2>/dev/null | grep -q "origin/$PARENT_BRANCH"; then
    echo "❌ Parent branch not found: $PARENT_BRANCH"
    echo "   The bug's parent branch must exist before creating a bug fix branch."
    exit 1
fi

git checkout "$PARENT_BRANCH"
git pull origin "$PARENT_BRANCH"

DEV_BRANCH="dev/ghi-{bug_id}-bug-{scope_prefix}{slug}-{username}"
git checkout -b "$DEV_BRANCH"
git push -u origin "$DEV_BRANCH"
echo "✓ Created bug dev branch $DEV_BRANCH (from $PARENT_BRANCH)"
```

##### Bug Workflow Does NOT Update Sprint Status

Bug fixes are NOT tracked in `sprint-status.yaml`. They are tracked via GitHub Issues with `bug` label linked to the parent project issue.

```

  Create a spec file first before running prepare-repos.

  Specify the story spec path:
  /tdgs-aidlc-prepare-repos implementation-artifacts/{story-spec-file}
```

## Configuration Reference

Expected structure in `.github/i2a-config.yml`:

```yaml
worker_repos:
  backend-service: "org/backend-service-repo"
  frontend-ui: "org/frontend-ui-repo"
  database: "org/database-repo"
```

Each key is the service identifier used throughout AIDLC prompts. The value is the `<github-org>/<repo-name>` string. This file is populated automatically by `/tdgs-aidlc-setup-workspace` from detected workspace repositories.
