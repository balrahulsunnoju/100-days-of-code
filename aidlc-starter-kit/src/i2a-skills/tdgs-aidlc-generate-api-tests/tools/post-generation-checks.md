# Post-Generation Validation Gate (Checks 1–20)

## Overview


> ⚠️ **BEFORE executing tests**, perform these automated checks on all generated collections. **DO NOT PROCEED to Step 6 until ALL checks pass.** If any check fails, fix the violations and re-run the checks. This gate is NOT optional — skipping it is the #1 cause of broken test suites.

**Check 1 — Model compliance (MANDATORY — run FIRST):** for EVERY request with a JSON body, verify EVERY field exists in the corresponding `@RequestBody` model class (recursively for nested DTOs). **Re-read the model class** — do NOT rely on discovery memory. Remove any field not in the model (HARD FAILURE; common offenders: catalog fields blindly copied). **Field name mapping:** if a catalog token uses the catalog field name as JSON key instead of the model field name, fix the JSON key to match the model (token PATH stays as catalog YAML key; JSON key = model field name). Display per-endpoint: `✅ POST /X — XRequest: 13 fields verified (0 invalid removed)` / `❌   └─ nested — NestedModel: removed extraField (not in model)`.

**Check 2 — Catalog compliance (when catalog found):**
- Every model field annotated `@NotNull`/`@NotBlank` is present in the request body (read directly from the model — catalog no longer carries `requiredFieldsByPayload`).
- Identity pool fields use `{{catalog.identityPool.*}}` tokens — NOT hardcoded values (even real identity values).
- Business identifiers (agency codes, org IDs, site codes) are baked into `data/valid-payloads.json` as literals verified per "Field Values Source-of-Truth Verification". Do NOT emit `{{businessConstants.*}}` — no such catalog section exists.
- If `apiChain[]` defines chains: every `{ fromStep, field, as }` MUST have `capture` metadata on the producer step's request AND `inject` + `{{captured.<as>}}` token usage in the consuming request body. **Capture/inject existence:** zero capture/inject when `apiChain[]` defines chains = **HARD FAILURE STOP**. **`{{captured.*}}` usage:** capture metadata alone is not enough — downstream bodies MUST use `{{captured.*}}` syntax = HARD FAILURE if missing.
- **Identity pool fields not hardcoded** — scan all bodies for identity-pool field names with hardcoded values = FAILURE. **Pool type names exist in catalog** — every `{{catalog.identityPool.{poolType}.*}}` token's `{poolType}` MUST match a `poolType:` in `identityPools[]` (HARD FAILURE; runner silently leaves unresolved → confusing 400). **Pool FIELDS exist in pool (HARD FAILURE — #1 source of `data-issue: identityPool record missing real value` at runtime):** every `{{catalog.identityPool.{poolType}.{fieldName}}}` MUST have `{fieldName}` literally in that pool's `fields[]` or `records[0].fields{}`. Common offenders: emitting `firstName`/`email` against pools containing only `dateOfBirth`/`licenseNumber`. Display per-token; **auto-fix:** for ❌ rows, REMOVE the catalog token and fall through the 9-step Field Value Resolution Chain per datatype. Re-run until ALL ✅.

**Check 3 — Assertion compatibility:** grep `unit_test.code` for chai methods; verify each is in the supported list (per "Assertion Methods" elsewhere). **Forbidden:** `.to.deep.equal()`, `.to.match()`, `.to.have.nested.property()`, `.to.throw()` (NOT supported by mini-chai fallback). `.to.be.an()` IS supported (alias for `.to.be.a()`). Auto-fix any unsupported usage.

**Check 4 — Field type consistency (MANDATORY — JSON quoting of tokens & literals):**
- Shared fields (IDs, reference numbers, status codes) use consistent types (string vs number) across ALL collections in ALL services.
- **Captured-token JSON quoting (HARD FAILURE — #1 cause of cascade chain breaks):** for EVERY `{{captured.{name}}}` in a body, determine the consumer's model field type (Java `String`/Python `str`/TS `string`/C# `string` → MUST be `"{{captured.{name}}}"` quoted; numeric Java `Long`/`Integer`/`int`/`BigDecimal` etc. → MUST be `{{captured.{name}}}` UNQUOTED). **Cross-check producer vs consumer:** if producer returns numeric but consumer model is String, MUST quote (runner writes captured numeric as string into JSON). Display verification rows; auto-fix quotes; re-run until ✅.
- **Catalog token quoting (same rule, additionally enforced — #2 silent type errors):** apply same string-vs-numeric quoting to `{{catalog.identityPool.<pool>.<field>}}`. For numeric/boolean: catalog YAML MUST be authored as the correct YAML scalar type (e.g., `accountId: 12345` not `"12345"`). Mismatches = HARD FAILURE.
- **Hardcoded literal type fidelity (MANDATORY — covers `data/valid-payloads.json` AND any inline literal in `body.text`):** every JSON scalar's shape MUST match the model's declared type. Java `Integer`/`Long`/`int`/`BigInteger` → JSON number unquoted (`"quantity": 1`, NOT `"1"`). Java `Double`/`Float`/`BigDecimal` → JSON number (BigDecimal MAY accept quoted string when `@JsonDeserialize` is configured — verify against controller). Java `Boolean` → JSON `true`/`false` unquoted. Java `String` → JSON quoted. **Optional/nullable left blank → JSON `null` or omit, NOT `""`** (empty-string fails `@Size(min=1)`/`@NotBlank`). Date/temporal `LocalDate`/`LocalDateTime`/`Instant` → quoted string in format from Per-Field Value Verification Procedure (NEVER a JSON number). Display per-field rows; auto-fix scalar shape; re-run until ✅. Mismatch = HARD FAILURE — do NOT proceed.

**Check 5 — Chaining order:** if `capture`/`inject` exist, verify capture-providers appear BEFORE inject-consumers in the request sequence. For each `inject`, confirm the corresponding `capture` exists on an EARLIER request in the same collection.

**Check 6 — Cross-service boundary compliance (G7 — verify against Phase 0 chain map):** for every Phase 0 row where "Cross-Svc?" is YES, verify the consumer test uses `{{catalog.stubs.<currentSvc>.<field>}}` (per G7), does NOT use `{{captured.*}}` from another service's producer, and unfulfilled stubs are recorded in `catalog-gaps.yaml` `requiredStubs:` + `test-data-catalog.yaml` `stubs.<svc>.<field>: TODO-PROVIDE-VALUE`. **HARD FAILURE patterns** (any one fails build, enforced by lint-collection.js): URL containing `{{<other-svc>_base_url}}` or another service's hostname; request name `SETUP:` anywhere; top-level folder named `Setup` (capital S); `<other-svc>_base_url`/`<other-svc>_context_path` keys in environments; `capture` block on a request targeting another service; literal cross-service value in any positive body (LINT-5); any `_skipReason` field anywhere (LINT-6). For EXTERNAL rows: NO request exists in ANY collection; downstream endpoints use catalog tokens or constraint-aware literals (NOT chain captures).

**Check 7 — apiChain endpoint existence (MANDATORY):** for EVERY endpoint in `apiChain[]` (producers AND consumers), verify it exists in actual controller source. Phantom endpoint = HARD FAILURE: `❌ apiChain references {METHOD /phantom} but no controller has it. Remove from catalog or fix path.` Path mismatch (catalog `/EndpointX`, controller `/v2/EndpointX`) → flag and use CONTROLLER path.

**Check 8 — Cross-service stub registry (MANDATORY when Phase 0 has Cross-Svc? YES):** for every cross-service consumer endpoint, verify: (1) positive body uses `{{catalog.stubs.<currentSvc>.<field>}}` (service-keyed, not endpoint-keyed) for each producer-sourced field; (2) `test-data-catalog.yaml` defines `stubs.<currentSvc>.<field>` (real value or `TODO-PROVIDE-VALUE`); (3) when TODO, `catalog-gaps.yaml` `requiredStubs:` includes `{ consumerService, consumerEndpoint, field, producerService, producerEndpoint }`. **HARD FAILURE:** any `_skipReason` field (LINT-6); collection-level `skip` on cross-service consumers instead of runnable request + stub token; hardcoded cross-service literals (LINT-5).

**Check 9 — UI-consumed version compliance:** every test path MUST appear in `uiAllowedPaths[]` (built in Section 3c by union-ing UI source + `uiScreens[].endpoints[].endpoint`). HARD FAILURE: `❌ Collection includes "POST /v4/Foo" but UI calls "POST /v5/Foo". Drop the legacy version per Section 3c.` Conversely, UI path with NO test → list in gap analysis as `Reason: "UI-consumed but missing test coverage"` — also HARD FAILURE.

**Check 10 — Domain-invariant AND polymorphic variant coverage (MANDATORY when applicable):**
- **10a — Business-rule variants:** every domain invariant detected at generation time (model `@Id`/`@GeneratedValue` first-create rule, conditional-required field rule, KB `business-rules-catalog.md` rule) MUST have at least one test with the expected behavior. Tag with rule ID `[BR-XXX]` when KB provides one. Without `businessRules` in catalog → best-effort (warnings, not HARD FAILURE).
- **10b — G12 polymorphic variant coverage (HARD FAILURE when variants exist):** if PRE-GENERATION VARIANT ENUMERATION (G12) discovered N variants, the collection MUST contain ≥1 positive + ≥1 negative (variant-specific field, not shared parent) + ≥1 edge/boundary PER variant (or justified `N/A`). Emit the VARIANT COVERAGE VERIFICATION table; ANY variant with 0 in Positive = HARD FAILURE; ANY variant with 0 in BOTH Negative AND Edge-Case = soft warning. SKIPPED for non-polymorphic services.

**Check 11 — No literal `{{...}}` tokens left after generation (MANDATORY):** grep every collection JSON for regex `\{\{(?!catalog\.identityPool\.|captured\.|\$).+?\}\}` — any unrecognized `{{...}}` = HARD FAILURE. Allowed: `{{catalog.identityPool.<pool>.<field>}}`, `{{captured.<name>}}`, Insomnia built-ins (`{{$randomUUID}}`, `{{$timestamp}}`, `{{$isoTimestamp}}`, `{{$randomInt}}`), faker tokens (Node-fallback closed list per setup-api-tests resolver: `{{$randomFirstName}}`, `{{$randomLastName}}`, `{{$randomFullName}}`, `{{$randomEmail}}`, `{{$randomPhone}}`, `{{$randomStreetAddress}}`, `{{$randomCity}}`, `{{$randomState}}`, `{{$randomZip}}`, `{{$randomDate}}`, `{{$randomGender}}`). Anything else (e.g., `{{$randomCompanyName}}`, `{{catalog.constant.*}}`, `{{businessConstants.*}}`) = generator hallucination or removed-section reference → runtime resolver leaves as literal text, API rejects body. Replace with typed-placeholder literal or run `/tdgs-aidlc-setup-testdata` to add the missing pool.

**Check 12 — Catalog override compliance (MANDATORY when catalog `identityPools[]` is present):** for EVERY field in EVERY positive (and SETUP) body recursively, walk the data-source decision tree and verify the chosen source is the FIRST matching rule. If a field name matches `catalog.identityPool.<pool>.<field>` (case-insensitive) AND pool's `class === 'external-required'`, body MUST use the catalog token — NOT a hardcoded literal and NOT faker.
- **Semantic synonym mapping (apply BEFORE concluding "no pool match"):** model field names rarely match pool field names character-for-character. Treat as semantic equivalents (case-insensitive, substring-tolerant): `email`/`emailAddress`/`contactEmail`/`recipientEmail`/`shipEmail` ⇄ pool fields containing `email`; `phone`/`phoneNumber`/`mobile`/`cell`/`shipPhone` ⇄ pool fields containing `phone`/`mobile`; `firstName`/`fname`/`givenName`/`forename` ⇄ `firstName`/`first_name`/`givenName`; `lastName`/`lname`/`surname`/`familyName` ⇄ same; `birthDate`/`dob`/`dateOfBirth` ⇄ same; `ssn`/`socialSecurityNumber` ⇄ pool `ssn` (`ssnLast4` only when model is also 4-digit); `dlNumber`/`driverLicense`/`licenseNumber` ⇄ same; `addressLine1`/`street`/`streetAddress` ⇄ pool `street`/`addressLine1`; `city`⇄`city`; `state`⇄`state`; `zip`/`postalCode`⇄same; `cardNumber`/`creditCard`/`paymentNumber` ⇄ pool `number` on `payment-card`-class; `cvv`/`securityCode` ⇄ `cvv`.
- **Format-compatibility veto (after synonym match):** if the pool value would fail model validation (catalog `dob` ISO `YYYY-MM-DD` vs model `@ValidDate` `MM/dd/yyyy`; catalog `ssnLast4` vs model 9-digit `ssn`), DO NOT emit the catalog token — use deterministic placeholder + emit `⚠️ Pool {pool}.{field} format incompatible with model {Class}.{field} ({reason}); using deterministic placeholder.`
- HARD FAILURE example: `❌ POST /X body field email = "placeholder@example.test" (literal), but catalog.identityPool.recipient-email.email exists and is available. FIX: replace with "{{catalog.identityPool.recipient-email.email}}".`
- **Auto-fix loop (MANDATORY):** emit FIX list, apply in-place, re-run Checks 12 + 11 — only proceed when both pass with `0 violations`.
- **Console summary (always emit):** `Check 12 — catalog override: scanned {N} fields across {M} requests in {K} collections — wired {W} to catalog tokens, {S} skipped (format-incompat), {V} VIOLATIONS auto-fixed.`
- SKIPPED with note when catalog has no `identityPools`.

**Check 13 — Cross-service env-var leak detection (MANDATORY — HARD STOP):** scan all `url` and `body.text` for tokens matching `\{\{\s*[a-z0-9][a-z0-9_-]*_(base_url|context_path)\s*\}\}` that are NOT the consumer's own `base_url`/`context_path`. HARD FAILURE per G7: remove any request that would call another service at runtime; replace cross-service field needs with `{{catalog.stubs.<currentSvc>.<field>}}` on a runnable consumer request in THIS service's collection. Do NOT add `<other-svc>_base_url` env keys or `_skipReason` metadata. Defense-in-depth for Check 6.

**Check 14 — Positive payload realism + PII safety (MANDATORY when model has optional fields):**

*Part A — Realism (every model field, not a curated subset):* for EVERY positive test, parse body recursively and read corresponding `@RequestBody` model. Compute `omitted = modelFields − bodyFields`. **HARD FAILURE if omitted ≠ ∅** EXCEPT for the single "minimal positive" variant per endpoint required by the Required-vs-Optional Field Strategy. A test counts as minimal-positive ONLY when (preferred order): (1) **metadata flag (preferred — language/case/whitespace-immune):** `metadata.variant === "minimal"` on the request/unit_test resource — generators MUST emit this for every minimal variant; OR (2) **name-suffix fallback (back-compat):** test name contains `Minimal positive` (case-insensitive) or explicit `(minimal-positive)` suffix. Metadata wins when both present. Do NOT rely on name-only detection — translation/rename silently breaks the exemption. Every OTHER positive (default + every chain step) MUST include every model field — no "optional means skip" exception. Optional fields exercise mappers/audit logs/DAO branches/serializers that minimal payloads silently bypass. For minimal-positive: `omitted` MUST equal exactly the optional (non-required) field set; omitting a REQUIRED field is still HARD FAILURE. Resolve missing fields via canonical **Field-Derivation Hierarchy P0–P6** in the Pre-flight Ground-Truth Hierarchy at top of file (P0 catalog → P1 captured → P2 UI literal → P3 KB → P4 DDL/DAO → P5 DTO annotation → P6 typed-placeholder). The legacy 4-rule wording is **superseded** — faker is restricted to closed runner token list and FORBIDDEN for PII fields. For nested DTOs recurse; for `List<T>`/array fields populate ≥1 realistic entry satisfying T's full-field rule.

*Part B — PII safety (HARD STOP — NEVER faker on identity fields when a pool exposes them):* PII field set (case-insensitive, camelCase/snake_case variants): contact (`email`/`emailAddress`/`phone`/`phoneNumber`/`mobile`/`fax`); identity names (`firstName`/`lastName`/`middleName`/`fullName`/`name` on person/applicant DTO/`motherName`/`fatherName`/`spouseName`); government IDs (`ssn`/`socialSecurityNumber`/`driverLicense*`/`dlNumber`/`passport*`/`taxId`/`nationalId`); demographics (`dateOfBirth`/`dob`/`birthDate`/`gender`/`race`/`ethnicity`). For EVERY positive body field whose name matches: if ANY `external-required` pool exposes a matching field → MUST be `{{catalog.identityPool.<pool>.<field>}}` (faker/literal = HARD FAILURE — risk: faker email could reach real SMTP gateway in non-isolated envs); if NO pool exposes it → use deterministic NON-real typed-placeholder (`"noreply@example.com"` (RFC 2606), `"555-0100"`, `"PLACEHOLDER-ID"`) per P6. Faker for PII forbidden in BOTH cases. If catalog has NO pool for a required PII field, generate with typed-placeholder + tag `(uses typed-placeholder for <field>)` for correct report classification. Prefer regenerating catalog (`/tdgs-aidlc-setup-testdata`) when field is recurrent.

*Part C — Auto-fix:* regenerate body using data-source tree, with faker fallback ONLY for non-PII filler (city/state/zip/street/country/generic free-text/list items).

**Check 15 — Chain-independent negative & edge tests (MANDATORY when chains exist):** for EVERY negative/edge test (folder name `Negative`/`Edge-Case` OR test name contains `Missing required`/`Invalid format`/`XSS`/`SQL`/`boundary`), grep `url` and `body.text` for `{{captured.` — ANY reference = HARD FAILURE. FIX: replace with literal invalid value like `"INVALID_999999"` and update test name `(uses INVALID_999999 to bypass chain)`. Guarantees that when an upstream returns 400, downstream validation tests still run and surface real defects instead of silently skipping.

**Check 16 — Positive chain integrity (MANDATORY when chains exist — HARD STOP):** the "positive chain shouldn't break" guarantee depends on five preconditions verified BEFORE generation finishes. Failing this guarantees runtime cascade-skip. For every chain in `apiChain[]`: **(1) Producer payload fully populated** (satisfies Check 14 Part A — thin payload returns 400 → captures nothing → entire downstream chain skips); **(2) Capture path resolves** — for each `capture` JSONPath, producer's response model exposes the path (HARD FAILURE: `❌ Chain captures $.foo but ResponseModel does not declare a foo field — capture silently undefined → consumer fails with "no such captured value".`); **(3) All chain inputs have catalog data** — for every `{{catalog.*}}` token, catalog has ≥1 `available` record/value in target environment (HARD FAILURE: `❌ Chain requires catalog.identityPool.<pool>.<field> but pool has 0 available records for env=local. FIX: run /tdgs-aidlc-setup-testdata to add records.`); **(4) Cross-service chains have env vars defined** (re-confirm Check 13); **(5) No optional-field minimalism on chain steps** — chain steps are POSITIVE by definition; required-only often satisfies bean validation but fails business validation (DAO insert, mapper). Single most important gate against the failure mode where step 1 returns 400 → steps 2-N skip → report claims "12 passed, 6 skipped" but the 6 skips were the entire interesting path.

**Check 17 — OpenAPI response-schema validation (MANDATORY when KB OpenAPI is present):** industry-standard contract testing requires EVERY positive response body to validate against documented OpenAPI schema (not just status code + selected property assertions). Without this, producer/consumer drift goes undetected. For EVERY positive test (2xx) on an endpoint with KB OpenAPI: (1) resolve `paths.<path>.<method>.responses.<status>.content.application/json.schema` (resolve every `$ref`); (2) inject AJV via the `Ajv` arg passed by the test-runner's `AsyncFunction` (`insomnia.addFormats` exposes `ajv-formats`):
```javascript
const resp = await insomnia.send();
expect(resp.status).to.equal(200);
const body = JSON.parse(resp.data);
const ajv = new Ajv({ allErrors: true, strict: false });
insomnia.addFormats(ajv);
const validate = ajv.compile(<inlined-schema>);
const valid = validate(body);
expect(valid, JSON.stringify(validate.errors)).to.be.true;
```
(3) `<inlined-schema>` MUST be inlined at generation time (not loaded at runtime — self-contained, no KB dir dep at execution). HARD FAILURE if any positive on a KB-documented endpoint lacks schema validation. SKIP for `schemaSource: code-fallback` (no KB entry) AND non-JSON responses (PDF/binary). Catches producer/consumer drift the moment a field is renamed/removed even if no consumer assertion explicitly references it.

**Check 18 — Test de-duplication (HARD FAILURE):** two tests are duplicates if they assert the SAME boundary on the SAME field on the SAME endpoint with the SAME identity pool. Algorithm: fingerprint = `sha1({method}|{path}|{field}|{boundary-class}|{identity-pool}|{expected-status})` where boundary-class ∈ {`min`, `max`, `null`, `pattern-violation`, `xss`, `sql-injection`, `ssrf`, …}. If ≥2 share fingerprint, all but FIRST are duplicates → auto-remove from collection JSON and report. If duplicates >5% of total → WARNING (review Test Count Budget Reconciliation block — discovery may be over-expanding variants).

**Check 19 — Cross-service stub coverage (HARD FAILURE):** enforces G7.2/G7.3. Every leaf field in every positive body whose value originates from a DIFFERENT service MUST resolve through `{{catalog.stubs.<currentSvc>.<field>}}` AND that catalog path MUST hold a non-placeholder value (`"TODO-PROVIDE-VALUE"` = missing). Algorithm: (1) build producer-field index from `apiChain[].steps[]`; (2) for every leaf field NOT resolved via `{{captured.*}}` (intra-service) or `{{catalog.identityPool.*}}` (PII), look up in producer index — if `producerService` ≠ current service, MUST be exactly `{{catalog.stubs.<currentSvc>.<field>}}`. Hardcoded literals, `{{captured.*}}` (wrong service), faker, identity-pool tokens for cross-service producers all FAIL. Catalog MUST hold non-placeholder value. **Auto-fix actions:** wrong token form → rewrite; missing catalog entry → invoke G7.3 (append `stubs.<currentSvc>.<field>: TODO-PROVIDE-VALUE` + `catalog-gaps.yaml` `requiredStubs:` row, do NOT block — test stays `data-issue` until real value supplied); hardcoded literal LOOKING like cross-service identifier (matches `/^(order|trace|receipt|confirmation|transaction)Number$|^transactionId$/i`) → STOP and ASK user `❓ Field {field} on {endpoint} appears to be cross-service identifier hardcoded as "{value}". Move to stubs.{currentSvc}.{field}? (y/n)` — do NOT silently rewrite (may be a deliberate known-good DB value). **Reverse check (orphan stubs):** every entry under `stubs.<currentSvc>.*` MUST be referenced by ≥1 test in current collection — orphans get WARNING (not HARD FAILURE; may be reserved for future tests). Catches the failure mode where a consumer collection references `{{captured.orderNumber}}` (which can never resolve in backend-direct test against the consumer service) when the producer is actually a different service.

**Check 20 — Assertion category strictness (HARD FAILURE — audit-derived F1/F6):** Grep all `unit_test.code` and enforce:
- **Positive tests (folder=Positive OR name lacks Negative/Edge/Security prefix):** grep for `resp.status).to.be.oneOf(` or `response.status).to.be.oneOf(` = HARD FAILURE. Grep for `resp.status).to.be.within(` = HARD FAILURE. Status assertion MUST be ONLY `to.equal(200)` or `to.equal(201)`. NOTE: `to.be.oneOf`/`to.be.within` on NON-STATUS targets (body fields, headers, elapsedTime) remain valid in positive tests.
- **Security/Injection tests (folder=Edge-Case AND name contains XSS/SQL/injection/traversal/command):** `resp.status).to.equal(200)` = HARD FAILURE. MUST have `to.not.equal(200)` AND `to.be.within(400, 499)` on status.
- **Data file emptiness:** for each `data/*.json` file generated, `jq length` MUST be > 0 — empty file = HARD FAILURE.
Display: per-category assertion audit table (category | total tests | compliant | violations | auto-fixed).
