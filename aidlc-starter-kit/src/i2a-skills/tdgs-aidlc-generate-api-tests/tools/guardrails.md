# Guardrails (G1–G25)

## Guardrails (Non-Negotiable, Read First)

### G1 — Application-agnostic
No specific app/vendor/service/field/path names hard-coded. Discover endpoints, request/response models, and validation from controllers + KB at runtime.

### G2 — Discover-before-generate
Ground every test in: (a) controller annotations (`@RestController`, `@GetMapping`, `@RequestBody`, validation annotations) (b) KB OpenAPI specs (c) `test-data-catalog.yaml.apiChain[]` (d) **client UI caller-side payload construction** (the wire-shape ground truth — see Pre-flight Ground-Truth Hierarchy Source #4). If an endpoint exists in code but not in catalog, append it to `catalog-gaps.yaml` and ASK the user — do NOT generate against an ungrounded model.

> **Enforcement is mechanical, not prose.** Wire-shape grounding, DTO `List<>` variant coverage, service discriminator-branch coverage, and endpoint-surface filtering (controller ∩ gateway ∩ UI-caller) are checked by `audit-coverage.js` (see G25 in this prompt + G16b in the setup prompt). The previous reactive `🛑 #1/#2/#3 DOCUMENTED FAILURE MODE` callouts were deleted — they duplicated G12 (variant gate, line ~180) and Section 3c (endpoint gate, line ~1490) and added length without enforcement. The audit script runs the same greps the agent was supposed to run by hand, exits non-zero on any gap, and gates `npm test` via the existing `pretest` hook.

> **Generic by design.** `audit-coverage.js` reads `api-tests/config/audit-config.json` (auto-generated by setup based on detected framework — Spring/FastAPI/Express/.NET/Lambda) for the controller/DTO/service-impl glob patterns and discriminator-detection regexes. No hard-coded service names, no hard-coded field names. When optional artifacts exist (Apigee proxy bundles, UI repo `src/api/`), the script also enforces the **API-surface intersection rule**: a controller endpoint counts as an API gap only if it is BOTH gateway-exposed AND consumer-called. Dead controller methods (declared but not exposed and not called) are not gaps.

### G3 — Ask-don't-assume
If scope (full/issue), environment (local/test/stage), or chain selection is ambiguous, ASK.

### G4 — No hallucinated schemas, response shapes, or field values
- Request/response field **NAMES and NESTING STRUCTURE** must come from the source-code DTO (the `@RequestBody` model class and its nested types) — the DTO is the wire contract. KB OpenAPI is a supplementary source for constraints, examples, and documentation only. If KB OpenAPI field names or nesting differ from the DTO, the **DTO wins unconditionally** (KB OpenAPI specs are frequently stale, may flatten nested structures, or use outdated field names). Never invent fields. Never use KB OpenAPI field names in payloads without verifying them against the actual DTO source.
- `kbFieldValueMap` field-pinning extraction MUST use a strict regex: `/(?:field|attribute|column)\s+`?(\w+)`?\s+(?:is|must be|always equals)\s+`?([\w\d-]+)`?/i`. Loose prose matches MUST be discarded — no fuzzy NLP.
- Negative test invariants are bounded: max 5 negative variants per endpoint without explicit user opt-in for more.

### G5 — Prerequisite check
If `{service-repo}/api-tests/scripts/test-runner.js` does not exist, STOP with `❌ Run /tdgs-aidlc-setup-api-tests first`. If `test-data-catalog.yaml` does not exist, STOP with `❌ Run /tdgs-aidlc-setup-testdata first`. If a service is not health-probable on its expected port, STOP — this prompt NEVER auto-starts services.

### G6 — PII handling
Faker is FORBIDDEN on PII fields. **The canonical PII regex is defined ONCE in this prompt at Pre-flight item 3 below — it is the single source of truth referenced by every other prompt (do NOT duplicate the literal regex here in G6).** Address fields (`address`, `street`, `city`, `state`, `zip`, `postalcode`, `country`) are explicitly NOT PII per Pre-flight item 3. PII values come exclusively from `identityPools[]` (`external-required` only).

### G7 — Cross-service / external dependency (single rule, no sub-rules)
For every leaf field in the consumer's request body, the source is decided in this strict order:
1. **Intra-service producer** (an earlier `apiChain[]` step in the SAME service declares this field in its response) → emit `{{captured.<fieldName>}}` and place a `capture` block on the producer.
2. **Cross-service producer** (an `apiChain[]` step in a DIFFERENT service declares this field) → emit `{{catalog.stubs.<currentServiceShortName>.<fieldName>}}`. If the catalog has no value at that path, write `TODO-PROVIDE-VALUE` to `stubs.<svc>.<field>` AND append `{ consumerService, consumerEndpoint, field, producerService, producerEndpoint }` to `catalog-gaps.yaml` under `requiredStubs:`. The runner classifies the test `data-issue` when the value is `TODO-PROVIDE-VALUE` (per `/tdgs-aidlc-setup-api-tests` Section 5 item 6) — green CI cannot mask a missing stub.
3. **No producer** → resolve via the standard Field Value Resolution Chain (catalog token → KB example → business rule → constraint-aware literal → faker for non-PII).

Service short name = repo stem after stripping `tx-ovra-` and `-service` (e.g. `tx-ovra-receipt-service` → `receipt`).

**Forbidden, with no exceptions:**
- Hardcoded literal cross-service values in any positive request body (e.g. `"orderNumber":"STUB_ORDER_12345"`). Always emit the `{{catalog.stubs.<svc>.<field>}}` token. The post-write linter LINT-5 rejects literals.
- The deprecated endpoint-keyed form `{{catalog.stubs.<endpoint>.<field>}}` or `stubs.<endpoint>.<field>:` in YAML. Service-keyed only.
- Generating a cross-service consumer test as `status: skipped` with `_skipReason` metadata. The runner does not honor `_skipReason`; the linter LINT-6 rejects it. Use the stub token + `TODO-PROVIDE-VALUE` and let the runner classify.
- A request whose URL targets another service's `base_url`. NEVER add `<other-service>_base_url` env vars. NEVER create a top-level `Setup` folder. Cross-service interaction belongs in a separate integration-test suite, not in component-level API tests.

**Chain capture — best-effort JSONPaths.** Wire every `apiChain[].capture[]` JSONPath the generator can infer from the producer's KB OpenAPI schema / DTO / response example. If the runtime response shape differs, the runner classifies the dependent downstream test `data-issue` (`<UNCAPTURED:>` sentinel) or `infra` (producer 4xx/5xx). Developer fixes the JSONPath in the collection — standard workflow, no special flagging.

### G9 — Idempotency
Merge into existing collections; preserve user-edited test cases; flag schema drift between catalog and existing collection for review.

**G9.1 — Audit-mode enforcement is mechanical, not prose.** Every collection write (new or merge) MUST pass `node {service-repo}/api-tests/scripts/lint-collection.js {service-repo}/api-tests/collections/<service>.json`. Non-zero exit → fix and re-run; do NOT continue. The linter (defined in `/tdgs-aidlc-setup-api-tests` G16) owns the formerly-prose checks LINT-1 through LINT-6:

- LINT-1 = assertion vocabulary allow-list (formerly Check 11 partial)
- LINT-2 = `{{...}}` token namespace allow-list (formerly Check 11)
- LINT-3 = pool/field existence in catalog (formerly Checks 12 + 14)
- LINT-4 = JSON parseability after token substitution (formerly Check 4 — type quoting)
- LINT-5 = no literal value matching a `stubs.*` path (formerly Check 19)
- LINT-6 = no `_skipReason` field anywhere (deprecated)

"Preserve user-edited test cases" applies to: (a) custom assertion code in `unit_test.code` (still subject to LINT-1), (b) custom test names, (c) custom env-var values. Schema-drift dimensions (DTO field completeness, catalog token correctness, PII safety, type quoting, chain capture wiring) MUST re-run regardless of who authored the request — failures surface through the linter, not through prose checklists. "Audit-only, no fixes" is NOT a valid mode — if you find violations you MUST apply auto-fixes (or stop and ask the user when an interactive choice is required, e.g., catalog override would change semantics).

### G11 — Shared contracts
- **`caseType` enum:** `positive | negative-validation | boundary | negative-business-rule`.
- **`passRate` formula:** `passed / (passed + failed + dataIssue + infra)` — `skipped` excluded. `0.0` when denominator is 0.
- **Status enum (per-service data-ledger):** `pass | fail | skip | data-issue | infra | generation-bug | unresolved-token`. Workspace `ledger.yaml` uses camelCase: `passed | failed | skipped | dataIssue | infra`. Dashboard maps between them.
- **Skip categories surfaced separately in dashboard:** `cross-service-dependency`, `data-issue`, `infra`, `quarantine`.
- **Multipart/form-data:** if endpoint declares `consumes: multipart/form-data` or `@RequestPart`, generate a FormData payload using a small fixture file (`api-tests/fixtures/sample.{pdf,png,csv}`); do not skip these endpoints.
- **`fieldFormatMap` location & schema (per-service config, NOT in catalog):** lives in `{service-repo}/api-tests/config/field-format-map.json` (per `/tdgs-aidlc-setup-api-tests` Section 4 — the format-coercion map is service-specific because each service's DAO/parser format is independent of the shared catalog). Top-level shape is **flat** (field-keyed): `{ "<fieldName>": { "from": "<canonical-format>", "to": "<service-format>" } }` (e.g., `{ "dateOfBirth": { "from": "MM/DD/YYYY", "to": "DD-Mon-YYYY" } }`). Format strings are one of: `MM/DD/YYYY`, `YYYY-MM-DD`, `DD-Mon-YYYY`, `NNNNNNNNN` (digits-only), `XXX-XX-XXXX`, or a custom `printf`-style template. **Do NOT add per-service coercion maps (`fieldFormatMap`) to the catalog YAML** — the coercion config is per-service to preserve catalog/runner separation. The catalog's `identityPools[].fieldFormats` block (written by `/tdgs-aidlc-setup-testdata`) is READ-ONLY metadata recording the canonical stored format — it is NOT a coercion map and MUST NOT be removed. The runner reads the per-service `field-format-map.json` once at startup and coerces values before injection.

### G12 — Mandatory variant/workflow coverage (HARD GATE — read FIRST)
> This is the MOST IMPORTANT guardrail. Generation MUST cover ALL discovered workflow variants — not just one type.

- **ALL polymorphic/variant fields MUST generate dedicated tests per variant value — across ALL test categories (positive, negative, edge-case).** If an endpoint accepts a `recordType` field with values `[typeA, typeB, typeC, ...]`, the generator MUST produce tests for EVERY value — not just the first one or two.
- **ALL record types in an apiChain workflow MUST have dedicated test paths.** If the KB or code shows an endpoint handles multiple document/record/transaction types, EVERY type gets its own complete chain run.
- **PRE-GENERATION VARIANT ENUMERATION (MANDATORY — do this BEFORE writing any collection file):**
  For EVERY endpoint whose `@RequestBody` DTO contains `List<*>` collection fields (polymorphic variants), you MUST:
  1. Open the parent DTO source file (e.g., the class used in `@RequestBody`)
  2. Extract ALL `List<VariantType>` fields — these are the variant types
  3. Display a variant checklist BEFORE writing collections:
     ```
     📋 VARIANT ENUMERATION for {endpoint}:
     Parent DTO: {ClassName}.java
     ┌────┬──────────────────────────────┬──────────────────────┐
     │ #  │ List<> Field Name            │ Variant DTO Class    │
     ├────┼──────────────────────────────┼──────────────────────┤
     │ 1  │ {fieldName1}                 │ {VariantClass1}      │
     │ 2  │ {fieldName2}                 │ {VariantClass2}      │
     │ 3  │ {fieldName3}                 │ {VariantClass3}      │
     │ ...│ ...                          │ ...                  │
     │ N  │ {fieldNameN}                 │ {VariantClassN}      │
     └────┴──────────────────────────────┴──────────────────────┘
     Total variants to generate: N
     ```
  4. **After generation, verify the count matches.** If the collection contains fewer positive test variants than the enumerated count, DO NOT proceed — go back and add the missing ones.
  5. **Do NOT rely on KB docs or OpenAPI alone to discover variants.** The DTO source file is the ONLY reliable source. KB/OpenAPI frequently lists only "common" types and omits less-common ones that still exist in code. The documented failure mode is: "generator reads KB, finds only a subset of types, generates tests for those, and silently skips the rest that only appear in the source DTO."
- **PER-VARIANT TEST COVERAGE MATRIX (MANDATORY for all categories):**
  Each discovered variant MUST have tests in ALL applicable categories — not just positive. The minimum coverage matrix per variant:

  | Category | Minimum per variant | What to test |
  |----------|-------------------|--------------|
  | Positive | 1 request + 1 unit_test | Valid payload with all required fields for that variant's DTO |
  | Negative — missing required | 1 per variant-specific required field | Omit each `@NotNull`/required field unique to that variant's DTO (fields shared across all variants need only 1 negative test total, not per variant) |
  | Negative — invalid format | 1 per variant-specific constrained field | Send invalid format for `@Pattern`/`@Email`/date fields unique to that variant |
  | Edge-case — boundary | 1 per variant | Boundary values specific to variant's constraints (e.g., max copies, date ranges, nested object limits) |
  | Edge-case — injection | shared across variants | XSS/SQLi tests may be shared (not per-variant) since injection targets field values not variant structure |

  **Rationale:** A polymorphic endpoint may validate different required fields per variant type. A generic "missing required field" test that omits a parent-level field does NOT cover a variant-specific required field (e.g., a variant's nested DTO requires `{nestedField}` but other variants don't have that nested object at all). Without per-variant negative tests, validation gaps for specific types go untested.

- **Enforcement:** After generation, produce a coverage summary table:
  ```
  ✅ VARIANT COVERAGE VERIFICATION for {endpoint}:
  ┌────────────────────┬──────────┬──────────┬───────────┬──────────┐
  │ Variant            │ Positive │ Negative │ Edge-Case │ Total    │
  ├────────────────────┼──────────┼──────────┼───────────┼──────────┤
  │ {variant1}         │ 1        │ 2        │ 1         │ 4        │
  │ {variant2}         │ 1        │ 3        │ 1         │ 5        │
  │ ...                │ ...      │ ...      │ ...       │ ...      │
  │ {variantN}         │ 1        │ 2        │ 1         │ 4        │
  ├────────────────────┼──────────┼──────────┼───────────┼──────────┤
  │ Shared (all)       │ —        │ 3        │ 4         │ 7        │
  └────────────────────┴──────────┴──────────┴───────────┴──────────┘
  ```
  If ANY variant has 0 in the Positive column, emit `❌ VARIANT COVERAGE GAP` and HALT. If ANY variant has 0 in BOTH Negative and Edge-Case columns, emit `⚠️ VARIANT NEGATIVE/EDGE GAP` as a warning (soft gate — proceed but flag for review).

- **This guardrail exists because the generator's documented failure mode is "generate tests for only one record type and group everything under generic Positive/Negative/Edge-Case folders, silently skipping all other types."** That failure mode is now a HARD STOP.
- **Collection folder structure MUST reflect variants:** When multiple variant values exist, organize by variant WITHIN each test category:
  ```
  {endpoint-group}/
  ├── Positive/
  │   ├── {variant-1} - valid payload
  │   ├── {variant-2} - valid payload
  │   └── {variant-N} - valid payload
  ├── Negative/
  │   ├── {variant-1} - missing {required-field}
  │   ├── {variant-2} - missing {required-field}
  │   ├── Shared - missing {parent-required-field} (applies to all)
  │   └── ...
  └── Edge-Case/
      ├── {variant-1} - boundary {constraint}
      ├── Multi-variant - combined payload with multiple types
      └── Shared - XSS/SQLi/injection (applies to all)
  ```
  This makes per-variant coverage visible in the collection tree and prevents the "one size fits all" generic negative test anti-pattern.

### G13 — DB transaction capture (MCP SQL Developer integration)
> When tests run against real services, every write-endpoint response MUST be captured into `dbRecordsCreated[]` with plain-text field values — no masking, no hashing. These values feed the dashboard's DB Transactions section, which QA uses with SQL Developer MCP to verify database state.

- **Capture ALL write-endpoint responses** — POST, PUT, PATCH, DELETE — regardless of HTTP status (2xx, 4xx, 5xx).
- **Extract business identifiers** from response bodies using catalog `apiChain[].capture[].field` first, then regex fallback: `/(id|number|code|reference|guid|uuid|key|token|trace|order|confirmation|receipt|tracking)$/i`.
- **Never leave `key`/`value` empty** — if nothing extractable, omit the entry entirely.
- **Plain text only** — values are test environment data (gitignored), used for `SELECT * FROM table WHERE field = 'value'` queries.
- **Output:** `db-transactions.json` alongside `dashboard.html` for MCP tool consumption.
- **Outcome field:** `created` (2xx), `attempted-failed` (4xx), `attempted-server-error` (5xx).

### G14 — Reports sync guardrail (single source of truth for all formats)
> Every report script MUST build ONE in-memory results object, then render ALL formats (.json, .md, .html) from that SAME object in ONE pass. Never re-read source data between format renders. After writing: assert `json.total === md.total === html.total`.

### G15 — Token Resolution & Stub Coverage Manifest (HARD GATE — emit BEFORE any collection write)
> This is the gate that eliminates the documented #1 failure mode: agent emits `{{catalog.identityPool.<pool>.<field>}}` for fields that do not exist in the pool, and emits cross-service consumer requests with no stub registered, producing a run with 0 real positive verifications. Past prompt versions stated the rules in prose (G7.3, Pool-field existence check) but did not require a verifiable artifact — the agent skipped enforcement. G15 makes enforcement a CHECKABLE pre-write deliverable.
>
> **G15.1 — Catalog Token Manifest (MANDATORY emit BEFORE writing any collection JSON).**
> For EVERY `{{catalog.identityPool.<pool>.<field>}}` token the agent plans to place in any request body in this generation pass, emit ONE row in a single markdown table named **CATALOG TOKEN MANIFEST**. Each row MUST be backed by a real lookup in the loaded catalog YAML:
>
> ```
> 📋 CATALOG TOKEN MANIFEST — {service} ({N} planned tokens):
> ┌────┬──────────────────────────────────────────────┬───────┬───────────┬──────────┬─────────────────────────────────┐
> │ #  │ Token                                        │ Pool? │ Field?    │ Decision │ Fallback (if REJECT)            │
> ├────┼──────────────────────────────────────────────┼───────┼───────────┼──────────┼─────────────────────────────────┤
> │ 1  │ {{catalog.identityPool.identity-instate.dl}} │ YES   │ YES       │ KEEP     │ —                               │
> │ 2  │ {{catalog.identityPool.identity-instate.fn}} │ YES   │ NO        │ REJECT   │ {{$randomFirstName}} (faker P8) │
> │ 3  │ {{catalog.identityPool.does-not-exist.x}}    │ NO    │ —         │ REJECT   │ {{$randomInt}} (constraint P7)  │
> │ ...│ ...                                          │ ...   │ ...       │ ...      │ ...                             │
> └────┴──────────────────────────────────────────────┴───────┴───────────┴──────────┴─────────────────────────────────┘
> ```
>
> Rules for filling each cell:
> - **Pool?** = `YES` iff `catalog.identityPools[].poolType === <pool>` for SOME pool. `NO` otherwise.
> - **Field?** = `YES` iff `<field>` appears in that pool's `fields[]` array OR as a key in any `records[].fields{}`. `NO` if Pool? is YES but field is absent. `—` if Pool? is NO.
> - **Decision** = `KEEP` iff Pool? is YES AND Field? is YES. Otherwise `REJECT`.
> - **Fallback** = the typed-faker / constraint-aware / typed-placeholder value the agent will emit instead, per the 9-step Field Value Resolution Chain (Pre-flight item 3). Choose by the field's datatype (faker P8 for names/email/phone/uuid; constraint-aware P7 for dates/ids; type-default P9 last). NEVER emit a literal known-good value for a PII field (G6).
>
> **HARD STOP:** If ANY row's Decision is `REJECT` AND the agent intends to emit that token anyway (rather than the Fallback), STOP. Replace the token with the Fallback in the planned body BEFORE writing the collection. The collection JSON MUST NOT contain any token whose row Decision is `REJECT` — that is a guaranteed `data-issue` at runtime.
>
> **Self-check before write:** After computing the manifest, scan every planned body string for `{{catalog.identityPool.*}}` and verify each match has a `KEEP` row in the manifest. Any token in a body without a matching `KEEP` row → STOP and rebuild the body.
>
> **G15.2 — Cross-Service Stub Manifest (MANDATORY emit BEFORE writing any collection JSON).**
> For EVERY leaf field in EVERY positive request body whose value originates from a DIFFERENT service per G7.2 step 2 (cross-service producer detected), emit ONE row in a single markdown table named **CROSS-SERVICE STUB MANIFEST**:
>
> ```
> 📋 CROSS-SERVICE STUB MANIFEST — {service} ({N} cross-service fields):
> ┌────┬─────────────┬────────────────┬──────────────┬─────────────────────────────────┬──────────────┬───────────────────────┐
> │ #  │ Consumer    │ Endpoint       │ Field        │ Stub Path                       │ Has Value?   │ Action                │
> ├────┼─────────────┼────────────────┼──────────────┼─────────────────────────────────┼──────────────┼───────────────────────┤
> │ 1  │ receipt     │ POST /SendMail │ orderNumber  │ stubs.receipt.orderNumber       │ YES (real)   │ EMIT TOKEN            │
> │ 2  │ receipt     │ POST /Generate │ orderNumber  │ stubs.receipt.orderNumber       │ YES (real)   │ EMIT TOKEN            │
> │ 3  │ verifletter │ POST /birthVer │ orderNumber  │ stubs.verificationletter.orderN │ NO (missing) │ WRITE TODO + ASK USER │
> │ ...│ ...         │ ...            │ ...          │ ...                             │ ...          │ ...                   │
> └────┴─────────────┴────────────────┴──────────────┴─────────────────────────────────┴──────────────┴───────────────────────┘
> ```
>
> Rules for filling each cell:
> - **Consumer** = the service whose collection is being generated (current service short name).
> - **Stub Path** = `stubs.<consumerShortName>.<fieldName>` — exact YAML path in `test-data-catalog.yaml`.
> - **Has Value?** = `YES (real)` iff the path exists in the catalog AND the value is NOT `"TODO-PROVIDE-VALUE"` AND NOT empty AND NOT null. `NO (missing)` iff the path is absent OR the value is one of the placeholder strings.
> - **Action**:
>   - `EMIT TOKEN` if Has Value? is YES → put `{{catalog.stubs.<consumerShortName>.<fieldName>}}` in the body. Test status remains pass/fail/data-issue per normal classification.
>   - `WRITE TODO + ASK USER` if Has Value? is NO → the agent MUST do all of the following BEFORE writing the collection JSON (this is the G7.3 enforcement that previously was prose-only and was being skipped):
>     1. Append the missing entry to `test-data-catalog.yaml` under `stubs.<consumerShortName>.<fieldName>: "TODO-PROVIDE-VALUE"` with a YAML comment line above it: `# TODO: cross-service value from <producerService> <producerEndpoint> — provide a known-good identifier or set CATALOG_STUB_<UPPER_SVC>_<UPPER_FIELD> at runtime`. Use `replace_string_in_file` / `create_file` to actually write the YAML — do NOT leave a "todo" in the agent's reasoning.
>     2. Append a one-line entry to `*-docs*/test-data/catalog-gaps.yaml` under `requiredStubs:` with `{ consumerService, consumerEndpoint, field, producerService, producerEndpoint }`.
>     3. STILL emit the `{{catalog.stubs.<consumerShortName>.<fieldName>}}` token in the body — at runtime the runner's **Pre-send Guard 6** (Cross-service stub TODO guard, defined in `/tdgs-aidlc-setup-api-tests`) sees the resolved literal `"TODO-PROVIDE-VALUE"` and classifies the test `data-issue` BEFORE any HTTP send (NOT `pass`, NOT `fail`), surfacing the gap on the dashboard's `data-issue` tile rather than masquerading as an application bug.
>     4. After ALL `WRITE TODO` rows are processed, emit ONE consolidated user prompt: `⚠️ {N} cross-service stub values need known-good identifiers. Listed in catalog-gaps.yaml. Provide values now (paste here) or set CATALOG_STUB_* env vars before re-running tests, then run /tdgs-aidlc-generate-api-tests again to refresh.` This prompt is informational — generation continues; the user can supply values later.
>
> **Self-check before write:** After computing the manifest, scan every planned body string for fields that appeared in a `WRITE TODO + ASK USER` row and verify the catalog YAML has been updated (re-read `test-data-catalog.yaml` from disk and confirm the new `stubs.<svc>.<field>` keys exist). If catalog write failed, STOP — do not proceed to writing collection JSON.
>
> **G15.3 — Manifest emission is unconditional.**
> Both manifests MUST be emitted EVERY generation pass — even when there are zero `REJECT` rows or zero `WRITE TODO` rows. A run with no rejects/todos still requires the agent to print the manifest with all `KEEP` / `EMIT TOKEN` rows so a reviewer can verify pool/field grounding without re-reading the catalog. The manifests are the proof-of-work for G15 and they replace prose-only assurances of "I checked the pool fields" — that prose was not enforceable and was demonstrably skipped in past runs.
>
> **G15.4 — Order of operations (locked).**
> 1. Load catalog YAML.
> 2. Discover endpoints + DTOs.
> 3. Plan request bodies (in memory only — do NOT write yet).
> 4. Emit CATALOG TOKEN MANIFEST. Apply REJECT → Fallback substitutions in the planned bodies.
> 5. Emit CROSS-SERVICE STUB MANIFEST. For every `WRITE TODO + ASK USER` row, write to catalog YAML and `catalog-gaps.yaml` BEFORE step 6.
> 6. Re-read catalog YAML from disk to confirm step-5 writes landed.
> 7. NOW write collection JSON, env files, etc.
> 8. Run the existing 20 post-generation checks.
>
> Any deviation from this order is a defect. Specifically: writing the collection JSON before step 4/5 produces a collection that contains tokens the catalog cannot resolve and that is exactly the documented failure mode this gate exists to eliminate.

### G16 — Frozen assertion contract (HARD GATE — every assertion the agent writes MUST be in the contract)
> The runner ships an explicit allow-list of assertion methods at `{service-repo}/api-tests/config/assertion-contract.json` (created by `/tdgs-aidlc-setup-api-tests` G15). The contract is the SINGLE SOURCE OF TRUTH for which `expect(...).<method>(...)` calls the runner's mini-chai actually implements.
>
> **Rule:** Before emitting any `unit_test.code` snippet, the agent MUST read `assertion-contract.json` and use ONLY methods listed there. The post-write linter LINT-1 re-verifies and fails the build on drift.
>
> **If a needed assertion method is not in the contract:** STOP. Do not invent a method name. Do not silently substitute. Ask the user whether to (a) extend the contract + runner mini-chai surgically to add the method (preferred when the assertion is genuinely needed), or (b) rewrite the test using existing contract methods (preferred when an existing method covers the case). Document the choice in the catalog gaps log.
>
> **Common drifts the contract prevents:** `to.be.within(min, max)`, `to.not.equal(...)`, `to.match(/regex/)`, `to.be.greaterThan(...)`, `to.be.lessThan(...)` — these MUST be in the contract emitted by setup. If a positive assertion form is missing, that is a setup-prompt defect; report it via the heal-check loop in `/tdgs-aidlc-setup-api-tests` Section 5 item 7, do NOT emit the call into the collection.

### G17 — Captured-token quoting (HARD GATE — type-correct token placement)
> Every `{{captured.<f>}}` and `{{catalog.stubs.<svc>.<f>}}` token placed in a JSON request body MUST be quoted iff the producer DTO field type is string-typed (`String`, `LocalDate`, `UUID`, enum). Numeric (`int`, `long`, `BigDecimal`), boolean, array, and object types MUST be unquoted.
>
> **Type lookup (NOT optional):** before emitting any token, the agent MUST consult `api-tests/config/field-format-map.json` (emitted by GENERATE per G21) for the producer field's declared Java type / OpenAPI `type+format`. If the map has no entry for the field, STOP and add the entry by reading the producer DTO source / OpenAPI schema. Guessing quoting from field-name heuristics is FORBIDDEN — it is the documented cause of past failures (e.g., `"orderNumber":{{captured.orderNumber}}` unquoted when DTO declares `private String orderNumber`).
>
> **Examples:**
> - String DTO field: `"orderNumber": "{{captured.orderNumber}}"`
> - Numeric: `"amount": {{captured.amount}}`
> - Boolean: `"isActive": {{captured.isActive}}`
> - Object: `"address": {{captured.address}}`
>
> The post-write linter LINT-4 substitutes a placeholder typed per the format map and rejects unparseable bodies.

### G18 — Conditional response assertion (HARD GATE — assert against the actual controller branch the variant exercises)
> When the same controller endpoint returns DIFFERENT response shapes depending on input (e.g., a search endpoint returns 200 with empty `[]` for "no match" and 200 with populated `[{...}]` for "match"), the agent MUST emit per-variant assertions that match the branch the variant actually exercises:
>
> - **Variant `not-found` / `no-match` / `empty-result`:** assert `expect(body).to.be.an('array').that.is.empty` (or the documented empty shape — `null`, `{}`, etc., per controller code reading).
> - **Variant `happy-path` / `found`:** assert structural fields (`expect(body[0]).to.have.property('orderNumber')`).
> - **Variant `validation-error`:** assert HTTP status is the documented 4xx AND body shape matches the documented error envelope.
>
> **Rule:** The agent MUST read the controller method body (or its KB OpenAPI response variants) BEFORE emitting assertions for a variant. Generic "every variant asserts the happy-path shape" is FORBIDDEN — it produces false-passes for negative variants and false-fails for empty-result variants. The post-write linter has no automated check for this (semantic) — Phase 0 discovery MUST emit a per-variant response-shape table and the agent self-checks against it before write.

### G19 — Positive Placeholder Allow-List (HARD GATE — when catalog/KB has no real value)
> The Field Value Resolution Chain (Pre-flight item 3) MUST resolve EVERY positive-body field through this strict order, and EVERY fallback MUST produce a value that is **format-correct for the field's declared type**. Junk literals (`TEST`, `FOO`, `XXX`), attack payloads (`<script>...`, `' OR '1'='1`, `;DROP TABLE`), HTML fragments, control characters, and empty strings are FORBIDDEN in positive bodies. The post-write linter LINT-7 + LINT-8 reject them.
>
> **Resolution chain (do NOT skip steps):**
> 1. **Catalog identityPool record** — `{{catalog.identityPool.<pool>.<field>}}` when pool/field exists per LINT-3.
> 2. **Catalog stub** — `{{catalog.stubs.<svc>.<field>}}` when the field is cross-service-produced per G7.
> 3. **KB OpenAPI `example:` value** — copy the literal example from the schema for that property.
> 4. **KB OpenAPI request-body example block** — copy the leaf value at the matching JSONPath.
> 5. **Controller test resource** (e.g., `src/test/resources/**/*.json`, `*-mock.json`) — copy matching field literal.
> 6. **Constraint-aware literal from schema** — derive from `pattern` / `minLength` / `maxLength` / `enum` / `format`.
> 7. **G19 Allow-List below** — format-correct placeholder by field-name + type.
> 8. **Type default** — `""` is FORBIDDEN; use the allow-list instead. For numbers `0`, booleans `false`, arrays `[]`, objects `{}` only when the schema permits.
>

> | Field-name regex (case-insensitive) | Type | Allow-list value |
> |---|---|---|
> | `^firstName$\|^fName$\|^givenName$` | string | `"Jane"` |

### G20 — Cross-pool field lookup (HARD GATE — the pool that OWNS the field, not the pool named after the service)
> When resolving a PII field via Step 1 of the G19 chain, the agent MUST search ALL pools in `catalog.identityPools[]` for one whose `fields[]` contains the target field name (case-insensitive). The pool is selected by FIELD OWNERSHIP, not by service name or workflow name.
>
> **Algorithm:**
> 1. For target field `<f>`, build candidate set `C = { p in identityPools : <f> (case-insensitive) IN p.fields }`.
> 2. If `|C| == 0` → fall through to G19 step 2 (catalog stub) or later.
> 3. If `|C| == 1` → emit `{{catalog.identityPool.<C[0].poolType>.<f>}}`.
> 4. If `|C| > 1` → disambiguate by the request's workflow context (which pool's `usedIn[]` lists the current endpoint or any endpoint in the same `apiChain[]`); record the choice in the CATALOG TOKEN MANIFEST (G15.1) `Decision` column.
>
> **Example failure mode this prevents (audit-confirmed defect from prior generation):**
> - Catalog has `identity-instate.fields = [dateOfBirth, ssnLast4, auditNumber, licenseNumber]` and `identity-outofstate.fields = [firstName, lastName, ssn, licenseNumber, dateOfBirth, street, city, state, zip]`.
> - Agent emitted `{{catalog.identityPool.identity-instate.firstName}}` because the workflow felt "in-state". WRONG — firstName is owned by `identity-outofstate` (single-element candidate set). Token resolves to `undefined` at runtime → test fails as `data-issue`.
> - Correct: `{{catalog.identityPool.identity-outofstate.firstName}}`.
>
> **Pool-name semantics are NOT field-presence guarantees.** A pool named after a workflow does not contain every field that workflow uses; pools group records that are LOOKED UP TOGETHER (e.g. for one TOAS verification, you need DL+audit+SSN-last4+DOB — those four go in one record together; the person's name comes from a DIFFERENT pool that joins on the SSN). LINT-3 enforces by rejecting any token whose `<field>` is absent from `<pool>.fields[]`.

### G21 — Schema-driven field format map (HARD GATE — one format per (endpoint, field), recorded mechanically)
> Date, datetime, decimal, and pattern-constrained string fields MUST share ONE format per (endpoint, field). The format is read from (in order): controller `@JsonFormat` / `@DateTimeFormat` annotation → OpenAPI schema `format:` / `pattern:` → controller test-resource example → KB documented format. Whichever wins is recorded in `api-tests/config/field-format-map.json`:
>
> ```json
> {
>   "<endpoint>": {
>     "<dotted.field.path>": { "javaType": "<class>", "jsonType": "<type>", "format": "<formatter>", "source": "@JsonFormat|@DateTimeFormat|openapi|test-resource|kb" }
>   }
> }
> ```
>
> **Use:** the value emitter MUST format every literal date/datetime/decimal value through this map. The post-write linter LINT-10 verifies that every literal value of a (endpoint, field) entry matches the recorded `format`. Mixed formats (`19-Jan-1961` AND `01/19/1961` AND `1961-01-19` for the same field across requests) reject with `endpoint <X> field <Y>: mixed formats {fmt1, fmt2}`.
>
> **Required-flag map sibling:** simultaneously emit `api-tests/config/field-required-map.json` recording each endpoint field's `required`/`@NotBlank`/`@NotEmpty`/`@NotNull` status. LINT-8 reads this to fire only on truly-required PII fields.

### G24 — Runner emission contract (HARD GATE — every test entry carries data-source + db-record arrays)
> The test-runner script (created at SETUP per G15/G16) MUST emit, for EVERY test entry in `test-results/results.json` and `data-ledger.json`:
>
> 1. `dataSources: [{ field: "<dotted.path>", source: "catalog|stub|captured|kb|schema-constraint|g19-allow-list|literal", token: "<original token or 'literal'>", resolvedValue: "<final value sent>" }, ...]` — ONE entry per top-level body field. Source of truth for dashboard's "Catalog records consumed this run" tile.
> 2. `dbRecordsCreated: [{ table: "<TABLE_NAME>", primaryKey: { "<col>": "<value>" }, businessKeys: { "<col>": "<value>" }, source: "response-body|response-header" }, ...]` — for every test whose HTTP method is POST/PUT/PATCH AND status is `pass`, populated from the response. Empty array `[]` only when the endpoint is documented as read-only / side-effect-free.
>
> **GENERATE responsibility:** when GENERATE patches the runner (or creates it on first run), it MUST verify the runner's per-test result-builder writes both arrays. If the runner is silent on either, patch surgically and re-run. The setup post-flight checklist (`/tdgs-aidlc-setup-api-tests` Section 5 item 9) lists both as PASS/FAIL gates — SETUP cannot complete with either missing.
>
> **Dashboard wiring:** the workspace dashboard (`tx-ovra-docs-sim/test-data/scripts/generate-workspace-dashboard.js`) reads `dbRecordsCreated[]` from each service's `data-ledger.json` and renders rows distinctly tagged by source folder (`Positive` → plain row, `Negative/Security` → row with red `security-test` badge so reviewers don't confuse XSS/SQLi-test artifacts with real positive data).

### G25 — Mandatory pre-finalize coverage audit (HARD GATE — mechanical, not prose)

> Before reporting "done" to the user, GENERATE MUST run `node {service-repo}/api-tests/scripts/audit-coverage.js {collection-path}` for EVERY collection it wrote or modified. Non-zero exit = HARD STOP. Fix the gap reported by the script, re-run audit, repeat until exit 0. Only then may GENERATE proceed to test execution and the final user report.
>
> **What the script enforces** (per setup G16b — see SETUP prompt for the full AUDIT-N spec):
> - **AUDIT-1** Every controller endpoint that is gateway-exposed AND consumer-called has ≥ 1 request in the collection (no UI-facing API gap).
> - **AUDIT-2** Every URL in the collection points to a real controller endpoint in THIS service (no phantom endpoints).
> - **AUDIT-3** Every endpoint with `List<*>` fields in its `@RequestBody` DTO has ≥ 1 positive request per List field (variant coverage — replaces deleted callout #2).
> - **AUDIT-4** Every endpoint whose service-impl branches on a request-body discriminator (`if/else if/switch/case` on a body field) has ≥ 1 positive request per discriminator value, UNLESS the consumer is annotated `(variant coverage inherited from <upstreamEndpoint>)` and that upstream IS in the catalog `apiChain[]` (carve-out — replaces deleted callout #3).
> - **AUDIT-5** (when Apigee proxy bundles or UI repo are present) Controller methods that are NOT gateway-exposed AND NOT UI-called are classified `not-API-surface` — no test required, but warn if tests exist (correct classification — would have prevented the false "5 missing endpoints" alarm).
>
> **The script is the single source of truth.** If the script says PASS, the agent reports "done". If the script says FAIL, the agent fixes the cited gap and re-runs. Prose self-audits ("I checked all variants") are forbidden — only the script's exit code counts. This rule replaces the three deleted `🛑 #1/#2/#3 DOCUMENTED FAILURE MODE` callouts; their content moved into the script's grep checks where it can actually be enforced.
>
> **Generic by design.** `audit-coverage.js` reads `api-tests/config/audit-config.json` for service-specific paths and framework-specific patterns. Setup auto-generates this config based on the detected stack (Spring/FastAPI/Express/.NET/Lambda). No hard-coded service names. No hard-coded field names. Same script, same exit-code contract, every service.
