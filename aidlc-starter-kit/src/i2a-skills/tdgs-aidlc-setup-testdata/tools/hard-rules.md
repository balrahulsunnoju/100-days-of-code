# Setup Test Data — Hard Rules

## Hard rules

1. **The UI is the source of truth.** Backend endpoints not imported by the UI are out of scope. When multiple versions exist, keep only the version the UI imports.
2. **API chain steps are sequenced by actual `.then()` / `await` order in the UI**, not by DTO field-name matching.
3. **Screen Flow is deduped AND attributed by ownership.** One row per UNIQUE screen with API calls. Each `{ method, path }` is owned by EXACTLY ONE screen — the one whose user action originates the chain. Mutation endpoints (`Create*`/`Save*`/`Submit*`-style) belong to the commit screen only; downstream screens that merely display the result do NOT re-list them.
4. **No API Flow / Chain section in the dashboard.** Screen Flow already lists every owned endpoint per screen — a separate chain table is pure duplication. `apiChain[]` lives in the catalog YAML only (consumed by the test runner), never rendered in HTML.
5. **Test Data shows only user-provided records.** No placeholder rows, no `derivable-from-ui` pools, no empty `upstream-generated` pools. The only allowed "empty" row is `0 records — paste needed` for an `external-required` pool with zero real entries.
6. **Flat tables, narrow page, minimum scrolling.** No big cards, no deeply nested expand/collapse, no tabs. Failure Analysis, Quick Actions, Run Manifest, DB Records Created, Slowest Tests, and Run History are conditionally rendered per their visibility rules in Step 4d.
7. **Only ask for `external-required` pools that are empty.** Never ask for `upstream-generated` or `derivable-from-ui` pools. Never re-prompt for a pool that already has records unless the user typed `update`.
8. **Quarantine threshold is 5 consecutive failures.** Not 3.
9. **In non-prod, records are reusable.** A failure does not burn a record — only 5 consecutive failures do.
10. **Discovery scans (Step 1) are business logic.** Before removing or simplifying any scan, confirm with the user.
11. **No app-specific names anywhere.** Application name comes from `catalog.application`; field names, endpoints, pool types, screen names come from workspace scanning.
12. **No pre-created scripts EXCEPT the workspace dashboard generator.** This prompt is an instruction set. Copilot writes the catalog YAML, asks only for what's needed, and generates `{docs-repo}/test-data/scripts/generate-workspace-dashboard.js` — the SINGLE reusable script enabling `/tdgs-aidlc-run-tests` to refresh the dashboard automatically. Regenerated every `setup-testdata` run (idempotent). No other scripts, no scaffolded `lib/`, no scaffolded `package.json`. Hard Rule 15 below specifies the on-disk write contract (atomic rename + advisory lock) every writer MUST honor.
13. **All artifacts go in `{docs-repo}/test-data/`.** Never workspace root, never service repos.
14. **Cross-app dashboard sync (MANDATORY when re-run after test executions).** When invoked AFTER API or functional test runs, regenerate the dashboard by reading the catalog + ledger + EVERY per-service `data-ledger.json` (API services: `*-service*/api-tests/test-results/data-ledger.json`; UI: `{ui-repo}/functional-tests/test-results/data-ledger.json`). Apply the per-service latest-run rule above (pick latest `runId` per service, then aggregate). The page-header summary tiles, the Test Data table's `Used`/`Failed` columns, and the Quarantine callout MUST reflect those aggregated latest-per-service totals. Then append ONE consolidated entry per cross-app run to `ledger.yaml` (sum across services that contributed within the last 24h window). If two ledger sources for the SAME service disagree on the latest `runId`, prefer the largest ISO-8601 timestamp; surface the discrepancy in the dashboard footer.
15. **Atomic catalog/ledger writes (MANDATORY).** Every writer of `test-data-catalog.yaml`, `ledger.yaml`, `dashboard.html`, OR a per-service `data-ledger.json` MUST: (a) write to a sibling `.tmp` file in the same directory, (b) `fsync` the tmp file, (c) atomically `rename(.tmp, target)`. The API test-runner, the functional test `globalTeardown`, and this prompt itself are concurrent writers of the catalog YAML, and this prompt's cross-app aggregation (Hard Rule 14) reads every service's `data-ledger.json` while those runners may still be writing — without atomic-rename, parallel service runs corrupt the catalog or the orchestrator reads a half-written JSON and crashes mid-aggregation.

    **Advisory lock (catalog only).** Before opening `test-data-catalog.yaml` for write, acquire an advisory lock via a sidecar `test-data-catalog.yaml.lock` file using `fs.writeFileSync(..., { flag: 'wx' })` (create-exclusive; fails fast with `EEXIST` if the file already exists). The lock file's content MUST be exactly two lines: line 1 = `process.pid`, line 2 = `Date.now()` (ms epoch). The lock MUST be released (file unlinked) inside a `try/finally` so unhandled exceptions still clean up. `ledger.yaml`, `dashboard.html`, and per-service `data-ledger.json` files do NOT require a sidecar lock because each has a single canonical writer (this prompt for the first two; the owning service's runner for the third) — atomic-rename alone is sufficient there. The canonical reference implementation (`acquireCatalogLock` + `persistCatalogStatus`) lives in `/tdgs-aidlc-setup-api-tests` Section 5; any other writer (functional `globalTeardown`, this prompt's own catalog writes) MUST mirror its behavior byte-for-byte.

    **Stale-lock recovery (MANDATORY).** When `wx` open fails with `EEXIST`, the writer MUST attempt recovery before waiting: read the lock file's two lines (`pid`, `startedAtMs`) and check `process.kill(pid, 0)` — if it throws `ESRCH` (process gone) OR the lock is older than 120s, log `⚠️ Reclaiming stale catalog lock (pid=<n> alive=<bool> age=<ms>ms)`, `unlink` the lock, and retry the `wx` open exactly once. Otherwise enter a bounded retry loop with 50–150ms randomized backoff (use `Atomics.wait` on a `SharedArrayBuffer` to block without CPU spin — a `while (Date.now() < t) {}` spin pegs one core). On each retry, re-attempt the stale-lock check before sleeping. Total wait timeout is 30s; on timeout, do ONE final stale-lock check and abort with a clear error including the holder PID and lock age so the user can investigate rather than corrupt the catalog by force.
16. **Ledger garbage-collection (MANDATORY).** `ledger.yaml` is append-only but bounded: keep at most the most recent 200 cross-app run entries (older entries pruned by this prompt on every regeneration). The dashboard's run-over-run trend chart only needs ~30 entries; 200 is a generous safety margin. Pruning happens BEFORE appending the new entry so the file never temporarily exceeds the cap.
17. **Runtime data-source fallback (cross-reference).** This prompt only seeds the catalog. AT TEST EXECUTION TIME, runners walk a strict 9-step **Field Value Resolution Chain** per field: (1) `{{catalog.identityPool.<pool>.<field>}}` for `external-required` pool fields, (2) `{{captured.<name>}}` from upstream `apiChain[]`, (3) KB OpenAPI `example`/`enum[0]`/`default`, (4) KB business-rules-catalog constants, (5) KB data-dictionary sample values, (6) UI source defaults (Yup/Zod, `initialValues`, dropdown options), (7) constraint-aware literal satisfying `@Pattern`/`@Size`/`@Email`/`@JsonFormat`/DDL `CHECK`, (8) faker for non-PII filler only, (9) type-default literal last resort. Faker is FORBIDDEN on PII fields (see `/tdgs-aidlc-generate-api-tests` Pre-flight item 3 and `/tdgs-aidlc-generate-functional-tests` Section 6). `derivable-from-ui` pools NEVER emit `{{catalog.identityPool.*}}` tokens — fields realized at GENERATION TIME via chain steps 3–7 for API tests and the `ui-source` rule for functional tests. Their `records: []` is intentionally empty; runtime resolver MUST NOT attempt catalog tokens against them.
18. **Production-environment protection (HARD STOP — MANDATORY).** Catalog records and the runtime resolver MUST NOT be loaded or used when the active environment is production. Detection (any one of the following triggers the block):
    - `process.env.NODE_ENV === 'production'`
    - `process.env.ENV` / `process.env.APP_ENV` / `process.env.STAGE` matches `/^(prod|production)$/i`
    - The selected env-file basename (e.g., `environments/prod.json`) matches `/^prod(uction)?\.(json|yaml|yml)$/i`
    - The catalog `application` field is set to a value matching `/^(prod|production)$/i`, OR the active environment selection (env file basename, env vars above) indicates production

    > **Note on application-tier metadata:** The current catalog schema stores `application` as a single string. Per-environment tiering (`application.environments[].tier`) is not part of the schema today; the production check above relies on environment-variable / env-file detection. Adding a multi-environment block to the catalog is tracked as a future enhancement — do NOT invent a `environments[]` array under `application` in this version.

    When triggered, the test-runner MUST:
    - SKIP all token resolution for `{{catalog.*}}` tokens (do NOT read `test-data-catalog.yaml`)
    - Mark every test that contains a `{{catalog.*}}` token as `data-issue` with reason `prod-env-protection: catalog data forbidden in production`
    - Refuse to write `data-ledger.json`, `dashboard.html`, or `ledger.yaml` updates derived from a production run
    - Emit a top-of-report banner: `🛑 Production environment detected — catalog data layer disabled. Test data catalog is for non-prod identity rotation only; running it against prod risks contacting real customers, mutating real records, or exposing PII in test artifacts.`

    Same defense-in-depth principle as PII / faker rules. Override NOT supported — testing against prod requires a separate manually-authored payload outside this framework.
19. **Re-run idempotency (MANDATORY).** This prompt is safe to re-run any number of times — it MERGES, never overwrites. Every re-run MUST honor the following invariants:
    - **`identityPools[].records[]`**: existing records are preserved by matching `records[].id` (or, when `id` is absent, by matching the full `fields{}` object). New records discovered from KB/UI scans are APPENDED. User-supplied real records are NEVER overwritten by a regenerated `PLACEHOLDER_*` record.
    - **`apiChain[]`**: chains are matched by `chainId`. Existing chains are updated in place (steps may be added/removed if endpoints changed); user-edited chain metadata (custom `notes`, `priority`, etc.) is preserved unless the underlying endpoint no longer exists.
    - **`uiScreens[]`**: screens are matched by `screen` name. Re-discovered endpoints are unioned with existing entries (de-dup by `(endpoint, target)` pair).
    - **`stubs` (optional, top-level):** user-authored cross-service stub overrides per G7. Re-runs MUST preserve every existing key under `stubs.*` verbatim — this prompt NEVER auto-generates, removes, or overwrites stubs (they are user-authored). If the entire `stubs:` block is absent, leave it absent. If present, copy it through unchanged.
    - **`ledger.yaml`**: entries are de-duplicated by `runId`. Re-running with the same `runId` overwrites that single entry; new `runId`s append. Hard Rule 16 still caps history at 200.
    - **`dashboard.html`**: regenerated from the merged catalog + ledger; the two `<script type="application/json">` blobs are replaced atomically (Hard Rule 15).
    - **Conflict resolution (precedence, highest first):** (1) user-edited fields explicitly marked with `# user-edited` YAML comment trailer are preserved verbatim, (2) real records with non-`PLACEHOLDER_*` values win over auto-discovered placeholders, (3) latest discovery scan wins for non-marked fields.
    - **Conflict with `/tdgs-aidlc-generate-api-tests` Cross-App Dashboard Refresh:** That prompt also rewrites the two dashboard JSON blobs at the end of every run. The two writers are reconciled by Hard Rule 15's atomic-rename + advisory lock — whichever finishes second sees the other's writes and merges by `runId`. Neither writer truncates the other's data. If a user runs `setup-testdata` AFTER a generate-api-tests run, the catalog is updated (new pool records, new chains) but ledger entries written by generate-api-tests are preserved.
    - **Display the merge summary** at the end of every re-run as a `RE-RUN MERGE SUMMARY` banner block listing per-section counts (existing preserved / new appended / removed) for: `identityPools`, `apiChain`, `uiScreens`, `stubs` (always "preserved untouched"), `ledger.yaml` (entries preserved + new `runId` appended), `dashboard.html` ("regenerated atomically").
